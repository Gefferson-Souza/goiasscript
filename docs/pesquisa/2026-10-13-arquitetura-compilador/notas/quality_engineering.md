# Quality Engineering for a Small TypeScript Compiler/Transpiler (GoiásScript rebuild, solo maintainer): testing, specification, quality gates, release and decision practice, state of practice 2026-10-13

> Method note. Version and date facts come from the npm registry (`https://registry.npmjs.org/<pkg>`) and GitHub releases/API, queried on 2026-10-13. Documentation claims come from the primary docs linked inline. "Local" facts were verified in the repository on the same day. Anything under **Inferences** is my own reasoning, not a sourced claim. Where a paper was only available as an abstract, the bullet says "abstract only".

## Compiler testing strategies: golden/baseline, round-trip, differential, property-based, fuzzing, mutation, test262, coverage and its limits

### Takeaway
Mature compilers anchor correctness on reviewed golden "baselines" (rustc UI tests, TypeScript baselines, Babel fixtures) plus execution tests and external corpora (esbuild runs test262 and other tools' suites). Randomized layers (fast-check, grammar-based generators, coverage-guided fuzzers) and mutation testing then measure and extend suite strength. Coverage is a hint for finding untested code, not a quality target: the strongest empirical evidence (Holmes and Inozemtseva, ICSE 2014) says exactly that.

### Cited Findings

#### Golden / snapshot ("baseline") tests
- rustc's UI suite keeps expected compiler output in `.stderr`/`.stdout` files beside each test, normally generated with `--bless` and then "inspect[ed] manually"; output is normalized to remove platform noise, and custom `normalize-stderr`-style rules exist — [rustc-dev-guide, UI tests](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/ui.md)
- The same tests carry inline `//~ ERROR ...` annotations (variants `//~^`, `//~|`, `//~v`, `//~?`); the guide says the redundancy with `.stderr` "helps avoid mistakes since the `.stderr` files are usually auto-generated", and `//~?` is preferred over the imprecise `//@ error-pattern` — [same source](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/ui.md)
- By default a UI test must fail compilation (`check-fail`); `check-pass`, `build-pass`, `run-pass`, `run-fail`, `run-crash` change the expectation, and `check-run-results` additionally compares the program's own output with `.run.stdout`/`.run.stderr` — [same source](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/ui.md)
- `known-bug` keeps a failing reproducer as "a sentinel that will fail if the bug is incidentally fixed", prompting the issue to be closed — [same source](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/ui.md)
- rustc test-writing rules: name tests after the behavior, not an issue number alone; its "Simple Test Sabotage Field Manual" lists anti-patterns (issue-number-only names, no comments, massive unminimized tests, unexplained `ignore-*` directives) — [best-practices](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/best-practices.md)
- rustc also runs a custom style checker ("Tidy"), tests the code examples in its published books through `rustdoc --test`, and runs a documentation link checker — [tests intro](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/intro.md)
- TypeScript (native port repo): new compiler tests live in `tsc/testdata/tests/cases/compiler/`; generated output goes to `tsc/testdata/baselines/local/` and accepted output to `tsc/testdata/baselines/reference/` — [TypeScript CONTRIBUTING](https://github.com/microsoft/TypeScript/blob/main/CONTRIBUTING.md)
- A git-tree listing of that repo (response flagged `truncated`, so counts are partial) shows each test stores several reference artifacts: emitted `.js`, `.types`, `.symbols` and `.txt` files — [GitHub trees API](https://api.github.com/repos/microsoft/TypeScript/git/trees/main?recursive=1)
- Babel fixtures: one directory per case with `input.js` + `output.js` + `options.json`; a `throws` key in `options.json` replaces `output.js` for expected errors; `exec.js` tests that run the produced code are "the second and preferred type"; `OVERWRITE=true` regenerates fixtures; `TEST_ONLY`/`TEST_GREP` filter runs — [Babel CONTRIBUTING](https://github.com/babel/babel/blob/main/CONTRIBUTING.md)
- esbuild separates fast development tests (`test-common`) from slow release tests (`test-all`) and has a `validate-builds` target that checks "published binaries are bitwise-identical to the locally-build binaries" — [esbuild Makefile](https://github.com/evanw/esbuild/blob/main/Makefile)

#### Round-trip, execution, differential and metamorphic testing
- Prettier's `--debug-check` prints an error "if it detects that code correctness might have changed", a built-in semantic-preservation check after reformatting — [Prettier CLI docs](https://github.com/prettier/prettier/blob/main/docs/cli.md)
- test262-parser-tests: every file in `pass/` has a twin in `pass-explicit/` (parentheses added); both "should be parsed to structures which are equivalent excepting unnecessary whitespace, comments, grouping parentheses, and semicolons" — [test262-parser-tests README](https://github.com/tc39/test262-parser-tests/blob/main/README.md)
- Differential testing (US 5,754,860, Digital Equipment Corp.): a generator with a grammar plus semantic constraints produces conforming programs run through two or more compilers; a failure means at least one deviates from the language standard; failing programs are then reduced — [patent abstract](https://patents.google.com/patent/US5754860). The 1998 McKeeman paper itself was not retrieved (bibliographic details only).
- Csmith (abstract only): randomized test generator; "more than 325 previously unknown bugs"; "every compiler we tested was found to crash and also to silently generate wrong code when presented with valid input"; it avoids undefined/unspecified behavior so wrong-code bugs are detectable — [OpenAlex record, PLDI 2011](https://api.openalex.org/works/doi:10.1145/1993498.1993532)
- Equivalence modulo inputs (abstract only): test inputs "induce a natural collection of the original program's EMI variants, which can help differentially test any compiler" and target miscompilations — [OpenAlex record, PLDI 2014](https://api.openalex.org/works/doi:10.1145/2594291.2594334)
- Metamorphic testing (abstract only): relies on "metamorphic relations, which are necessary properties of the target function or algorithm in relation to multiple inputs and their expected outputs" — [OpenAlex record, ACM CSUR 2018](https://api.openalex.org/works/doi:10.1145/3143561)
- "A Survey of Compiler Testing" (Chen, Patra, Pradel, Xiong, Zhang, Hao, Zhang; ACM CSUR 53(1), 2020-02-06) covers how to construct test programs, which test oracles to use, how to execute compiler tests efficiently and how to help developers act on discovered bugs (abstract only) — [Crossref](https://api.crossref.org/works/10.1145/3363562); [Semantic Scholar](https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3363562?fields=title,abstract,year,venue,citationCount)
- esbuild feeds external suites through itself: `make test262` clones tc39/test262 and runs `scripts/test262.js`; other targets run the UglifyJS, Rollup, Sucrase, Esprima and terser suites, and type-check tsc with a tsc built by esbuild — [esbuild Makefile](https://github.com/evanw/esbuild/blob/main/Makefile)
- rustc Crater compiles and tests every crate on crates.io to measure breakage; caveats: not all code is on crates.io, and only Linux x86_64 is covered — [Crater](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/crater.md)
- rustc-perf compares two compiler commits over "a large collection of popular crates" in fresh and incremental configurations — [perf testing](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/perf.md)

#### Property-based testing with fast-check
- fast-check is "Property based testing framework for JavaScript/TypeScript"; a property is "for all (x, y, ...) such that precondition(x, y, ...) holds predicate(x, y, ...) is true"; failures print the seed and shrink path, e.g. `Property failed after 1 tests (seed: 1527422598337, path: 0:0): ["","",""]`, `Shrunk 1 time(s)` — [fast-check README](https://github.com/dubzzz/fast-check/blob/main/packages/fast-check/README.md); latest 4.10.2, published 2026-09-19 — [registry](https://registry.npmjs.org/fast-check)
- Recursive structures (AST-like data) use `fc.letrec`; docs say "Prefer `fc.letrec` over `fc.memo`"; depth is bounded with `maxDepth` and a shared `depthIdentifier` (`fc.createDepthIdentifier()`), e.g. `fc.oneof({ maxDepth: 2 }, { arbitrary: tie('leaf'), weight: 0 }, { arbitrary: tie('node'), weight: 1 })` — [recursive structures](https://github.com/dubzzz/fast-check/blob/main/website/docs/core-blocks/arbitraries/combiners/recursive-structure.md)
- `fc.assert` throws a formatted error; `fc.check` returns `RunDetails`, which distinguishes failed predicate, too many precondition failures, interruption by `interruptAfterTimeLimit`, and success — [runners](https://github.com/dubzzz/fast-check/blob/main/website/docs/core-blocks/runners.md)
- `fc.configureGlobal({ numRuns })` shares settings but "fully resets" earlier global settings; `readConfigureGlobal` extends them — [global settings](https://github.com/dubzzz/fast-check/blob/main/website/docs/configuration/global-settings.md)
- `@fast-check/vitest` 0.5.0 (peer range `vitest ^4.1.0||^5.0.0`) provides `test.prop` in record or tuple notation and a "one-time random mode" (`g(fc.string)`); the connector "takes care of timeouts, lifecycle hooks and configuration" — [fast-check + Vitest guide](https://github.com/dubzzz/fast-check/blob/main/website/docs/tutorials/setting-up-your-test-environment/property-based-testing-with-vitest.md); [registry](https://registry.npmjs.org/@fast-check/vitest)
- QuickCheck (abstract only): properties are functions "automatically tested on random input", with custom generators; "random testing is especially suitable for functional programs because properties can be stated at a fine grain" — [OpenAlex record, ICFP 2000](https://api.openalex.org/works/doi:10.1145/351240.351266)

#### Grammar-based generation and fuzzing tools
- Grammarinator is an "ANTLRv4 grammar-based test generator", a random test generator/fuzzer — [README](https://github.com/renatahodovan/grammarinator)
- Jazzer.js 4.0.0 (published 2026-04-15) is a "coverage-guided, in-process fuzzer for the Node.js platform" based on libFuzzer — [README](https://github.com/CodeIntelligenceTesting/jazzer.js); [registry](https://registry.npmjs.org/@jazzer.js/core)
- Fuzzilli is a coverage-guided fuzzer for dynamic-language interpreters; it mutates a custom IL translated to JavaScript and needs engines built with coverage instrumentation, so it targets JS engines rather than transpilers — [README](https://github.com/googleprojectzero/fuzzilli)
- rustc's fuzzing guide: fuzzing is "any testing methodology that involves compiling a wide variety of programs"; reports should include a minimal standalone example and say the bug was found by fuzzing — [fuzzing guide](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/fuzzing.md)

#### Mutation testing (StrykerJS)
- StrykerJS 10.0.0 (2026-08-14): drops Node 20 (Node 22+ required); adds experimental TypeScript 7 support to the typescript-checker; adds mutant filtering and an empty-expression mutator; saves a partial incremental report on unexpected exit — [release notes](https://github.com/stryker-mutator/stryker-js/releases/tag/v10.0.0)
- Mutant states: Killed, Survived, No coverage, Timeout (counted as detected), Runtime error and Compile error (excluded from the score), Ignored; "Mutation score: detected / valid * 100" — [states and metrics](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)
- `thresholds` default `{ high: 80, low: 60, break: null }`; below `break` Stryker exits with code 1; all three values must be supplied together — [configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)
- `coverageAnalysis` defaults to `perTest`, which requires tests that "run independently of each other and in random order"; `ignoreStatic` requires `perTest` — [configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)
- Incremental mode (`--incremental`, since 6.2) stores `reports/stryker-incremental.json` and reuses killed-mutant results when the killing test still exists unchanged; the docs' example reuses 3731 results and runs only 234 mutants — [incremental](https://stryker-mutator.io/docs/stryker-js/incremental/)
- Vitest runner: bring your own vitest; `vitest.related` (default `true`) runs only tests related to the mutated files, and should be disabled when tests do not import source files directly (for example tests that call a server through an API); Stryker forces `coverage.enabled: false`, `singleThread: true` and `bail: 1` (0 when `disableBail` is set) — [Vitest runner](https://stryker-mutator.io/docs/stryker-js/vitest-runner/); peer range `vitest >=2.0.0` — [registry](https://registry.npmjs.org/@stryker-mutator/vitest-runner)
- TypeScript checker: type-invalid mutants are reported as CompileError (so they leave the score), checking is in-memory and supports project references; it always overrides `allowUnreachableCode: true`, `noUnusedLocals: false` and `noUnusedParameters: false` — [TypeScript checker](https://stryker-mutator.io/docs/stryker-js/typescript-checker/)
- Validity evidence (abstract only): across 357 real faults in 5 projects (321,000 LOC), "a statistically significant correlation between mutant detection and real fault detection, independently of code coverage", with "inherent limitations" — [Just et al., FSE 2014](https://api.openalex.org/works/doi:10.1145/2635868.2635929)
- Industrial practice (abstract only): Google uses diff-based probabilistic mutation analysis (skipping lines without statement coverage and "arid" lines) surfaced in code review for about 6,000 engineers — [State of mutation testing at Google, ICSE-SEIP 2018](https://api.openalex.org/works/doi:10.1145/3183519.3183521)

#### test262 and conformance subsets
- test262 is the conformance suite for ECMA-262/402/404; "over 50,000 individual test files" as of May 2025; "TC39 does not consider coverage to be complete"; Stage 4 entrance in the TC39 process "requires tests for new feature proposals" — [test262 README](https://github.com/tc39/test262/blob/main/README.md)
- Test files carry YAML front matter between `/*---` and `---*/`; `negative: { phase: parse|resolution|runtime, type: <ErrorConstructor> }` marks expected errors, and a test whose error arrives in a different phase "must be interpreted as failing"; `includes` pulls harness files; `flags` such as `onlyStrict`/`noStrict` control execution mode — [INTERPRETING](https://github.com/tc39/test262/blob/main/INTERPRETING.md)
- New tests need `description`, `esid` (the spec section id) and, for new features, `features` — [CONTRIBUTING](https://github.com/tc39/test262/blob/main/CONTRIBUTING.md)
- A Node.js runner exists (tc39/test262-harness) — [README](https://github.com/tc39/test262/blob/main/README.md)
- test262-parser-tests: `pass/`, `early/` (valid grammar but triggers early errors) and `fail/` (violates the grammar); files "are not intended to be evaluated, only parsed" and carry no metadata — [README](https://github.com/tc39/test262-parser-tests/blob/main/README.md)
- TC39 Stage 4 entrance includes "two compatible implementations which pass the Test262 acceptance tests" — [TC39 process](https://tc39.es/process-document/)

#### Coverage metrics and their limits
- Holmes and Inozemtseva: 31,000 test suites over five Java systems of up to 724,000 LOC; statement, decision and modified-condition coverage compared with mutation-based effectiveness; "low to moderate correlation between coverage and effectiveness when the number of test cases in the suite is controlled for"; "stronger forms of coverage do not provide greater insight"; coverage "should not be used as a quality target" though it is "useful for identifying under-tested parts of a program" — [ICSE 2014 paper (PDF)](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)
- Marick, "How to Misuse Code Coverage": coverage tools "are misused more often than they're used well"; they are "only helpful if they're used to enhance thought, not replace it" — [archived PDF](https://web.archive.org/web/2020id_/http://www.exampler.com/testing-com/writings/coverage.pdf)
- MC/DC is "the percentage of individual branch conditions that have been shown to independently affect the decision outcome"; it builds on branch coverage; clang offers `-fcoverage-mcdc` and an MC/DC subview for expressions with at most six conditions — [Clang source-based coverage](https://clang.llvm.org/docs/SourceBasedCodeCoverage.html); NASA's tutorial frames MC/DC for DO-178B level A aviation software — [NASA NTRS](https://ntrs.nasa.gov/api/citations/20010057789)
- Vitest coverage: providers `v8` (default) and `istanbul`; since v3.2.0, AST-based remapping makes V8 reports "identical to Istanbul"; inside an AI coding agent Vitest sets `skipFull: true` on the `text` reporter and adds `text-summary` — [coverage guide](https://github.com/vitest-dev/vitest/blob/main/docs/guide/coverage.md)
- Vitest thresholds: `lines`, `functions`, `branches`, `statements`, `perFile`, `autoUpdate` — [coverage config](https://github.com/vitest-dev/vitest/blob/main/docs/config/coverage.md); Vitest 5 breaking changes: glob thresholds no longer inherit `perFile`, `include`/`exclude` match more precisely — [migration guide](https://github.com/vitest-dev/vitest/blob/main/docs/guide/migration/index.md)
- Vitest 5 needs Node >= 22.12 and Vite >= 6.4, clears mocks by default, fails tests that do not await async assertions, and moves `bench` into a test-context fixture — [migration guide](https://github.com/vitest-dev/vitest/blob/main/docs/guide/migration/index.md); `@vitest/coverage-v8@5.0.4` pins `vitest` to exactly `5.0.4` as a peer — [registry](https://registry.npmjs.org/@vitest/coverage-v8)

### Inferences
- Suggested layering for a keyword-level transpiler (a design proposal assembled from the precedents above): (1) per-phase golden baselines (tokens, AST JSON, emitted JS, diagnostics with code and span) in `tests/conformance/<area>/<case>` files with a bless/overwrite command and PR-diff review (rustc, Babel, TypeScript pattern); (2) execution tests that run emitted JS and compare stdout/exit code (Babel calls these preferred); (3) a free oracle that every emitted program parses as valid JS; (4) fast-check properties; (5) differential "JS twin" programs; (6) Stryker mutation testing; (7) fuzzing for crash-freedom.
- Candidate fast-check properties (untested hypotheses): lexer lossless round-trip (concatenated lexemes plus trivia equal the source), monotonic non-overlapping token spans, determinism (same input gives byte-identical output, which also keeps baselines stable), whitespace/comment insensitivity, "result or typed GoiásScript error, never a raw TypeError/RangeError or hang", diagnostic spans always inside the source, and idempotence of any formatter. `fc.letrec` with `maxDepth` and a shared depth identifier is the documented way to generate nested expressions.
- If the language spec guarantees that code without goianês keywords passes through unchanged (a design decision I could not verify), then test262-parser-tests `pass/` and subsets of test262 become a large identity-property corpus; running real test262 tests written in goianês would require a lexer-aware inverse transliterator, which is a stretch goal, not a baseline. esbuild shows the pattern of cloning test262 and running it through the tool under test, but I did not read how its runner handles skips.
- With a core of roughly 2.2k lines, a full Stryker run should be cheap enough for every PR in incremental mode, with a full run nightly; the practical constraint is test design: `perTest` coverage needs order-independent tests, and `vitest.related` will not see tests that spawn the CLI as a subprocess, so keep unit tests importing modules directly and treat CLI end-to-end tests as a separate layer. Stryker's `break` is null by default; set it just under the measured baseline and ratchet upward.
- Treat line/branch coverage as a ratchet ("never decrease") plus a report of uncovered code, and use mutation score as the strength signal; this matches Holmes and Inozemtseva and Marick. MC/DC has no JS-native tool in my search (see Gaps), so branch coverage plus mutation is the pragmatic proxy.
- Use the rustc conventions that fit: diagnostics tests annotated with error code and span, an expected-failure marker as a `known-bug` sentinel, and behavior-based test names (consistent with the user's rule against phase markers in test titles). The 20 in-repo `.gs` examples plus code blocks from docs and the playground form a cheap Crater-style "ecosystem corpus" that must transpile and run in CI.
- Hot spot for a hand-written lexer: regex backtracking. A property-based scaling test (time versus input size) and the `eslint-plugin-regexp` rules `no-super-linear-backtracking` and `no-super-linear-move` target this class of bug ([plugin README](https://github.com/ota-meshi/eslint-plugin-regexp)).

## Language specification practice: EBNF grammar, language reference, conformance suites, versioning, deprecation

### Takeaway
Established languages specify grammar in a small, regular EBNF dialect, tag features with the version that introduced them, and test the spec through id-linked conformance suites. Compatibility policy is explicit: Go's source-level promise with enumerated exceptions, Rust's opt-in editions, Python's two-year minimum deprecation, and TypeScript's deprecate-in-6.0, error-in-7.0 cycle with an escape hatch.

### Cited Findings

#### Grammar notation and reference structure
- Go's spec defines its EBNF variant in eight productions (`Syntax`, `Production`, `Expression`, `Term`, `Factor`, `Group`, `Option`, `Repetition`); lowercase production names denote lexical tokens, CamelCase names denote non-terminals — [Go spec](https://github.com/golang/go/blob/master/doc/go_spec.html)
- Go marks features with `[Go 1.xx]` and ends with a "Language versions" appendix table of minimum versions; example: `0b1011` "will be rejected if the implied or required language version used by the compiler is older than Go 1.13" — [Go spec](https://github.com/golang/go/blob/master/doc/go_spec.html)
- The Rust Reference uses CAPITAL names for lexer tokens, italic CamelCase for syntax productions, postfix `?`/`*`/`+`, and `!` for negative lookahead; each rule carries a stable id such as `r[notation.grammar.syntax]` — [Rust Reference, notation](https://github.com/rust-lang/reference/blob/master/src/notation.md)
- test262 ties each test to the spec via the `esid` front-matter key (the section id), alongside required `description` — [CONTRIBUTING](https://github.com/tc39/test262/blob/main/CONTRIBUTING.md)
- TC39: from Stage 2 onward, semantics, API and syntax "must be described as edits to the latest published ECMAScript standard"; Stage 2.7 requires reviewers who are not authors of the spec text — [TC39 process](https://tc39.es/process-document/)

#### Conformance suites
- test262 and test262-parser-tests (details in the testing section above) are the reference model: metadata-driven expected errors by phase, and `pass`/`early`/`fail` directories with pass/pass-explicit equivalence — [INTERPRETING](https://github.com/tc39/test262/blob/main/INTERPRETING.md); [parser tests](https://github.com/tc39/test262-parser-tests/blob/main/README.md)
- rustc organizes UI tests by feature area and suggests a subdirectory per feature or RFC, e.g. `tests/ui/rfc1234-widgets/`; it enforces a tidy limit of 1000 entries per directory — [UI tests](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/ui.md)

#### Versioning and compatibility
- Go 1: "programs written to the Go 1 specification will continue to compile and run correctly, unchanged, over the lifetime of that specification"; compatibility is at source level; documented exceptions: security, unspecified behavior, specification errors, bugs, unkeyed struct literals, new methods — [Go 1 compatibility](https://go.dev/doc/go1compat)
- Go's GODEBUG: for permitted-but-breaking changes Go "first engineer[s] the change to keep as many existing programs working as possible", then adds a setting to opt back in; compatibility settings are kept "for a minimum of two years (four Go releases)" — [Go, Backwards Compatibility, and GODEBUG](https://go.dev/doc/godebug)
- Rust editions: features stabilized once are supported forever; backward-incompatible changes go into the next edition, opted into per crate; "crates in one edition must seamlessly interoperate with those compiled with other editions"; changes are "skin deep"; `cargo fix` automates migration (e.g. `async` becomes `r#async`) — [Edition Guide](https://github.com/rust-lang/edition-guide/blob/master/src/editions/index.md)
- RFC 2052: declare an edition "every two or three years"; an edition bundles stabilized features, polished error messages, updated tooling, a guide and updated book — [RFC 2052](https://github.com/rust-lang/rfcs/blob/master/text/2052-epochs.md)
- TypeScript 6.0 is a declared "bridge" release; its deprecations "can be ignored by setting `"ignoreDeprecations": "6.0"`", but "TypeScript 7.0 will not support any of these deprecated options" — [TS 6.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/); TS 7.0 turns them into hard errors and states that code compiling cleanly on 6.0 (with `stableTypeOrdering` on and no `ignoreDeprecations`) "should compile identically in TypeScript 7.0" — [TS 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- ECMAScript ships as yearly standard publications; Stage 4 proposals are integrated and "eventual[ly]" included in a yearly publication — [TC39 process](https://tc39.es/process-document/)

#### Deprecation policy examples
- PEP 387: behavior must not change incompatibly between consecutive releases unless through deprecation; with a yearly release cadence "the deprecation period must last at least two years"; a warning must appear for at least two minor releases and removal is preferably after five years; "soft deprecation" is documentation-only, issues no warning and schedules no removal — [PEP 387](https://github.com/python/peps/blob/main/peps/pep-0387.rst)
- Migration tooling is part of the policy at ESLint (codemods: `npx codemod @eslint/v9-to-v10`) — [ESLint v10 migration](https://github.com/eslint/eslint/blob/main/docs/src/use/migrate-to-10.0.0.md); and Rust (`cargo fix`, above). Vitest's migration guide ships a copyable agent prompt ("Migrate to Vitest 5. Fetch the migration guide ...") — [Vitest migration](https://github.com/vitest-dev/vitest/blob/main/docs/guide/migration/index.md)

#### Local baseline
- The repository's agent rules record past hard renames with no deprecation window ("Nunca voltar aos nomes antigos (`gspack`, `gsdebug`, `gsrepl`)") — [local: CLAUDE.md](<repo>/CLAUDE.md)

### Inferences
- Go's eight-production EBNF is the smallest adequate notation to adopt; give each production and each semantic rule a stable id and reference ids from conformance tests (test262 `esid` and Rust `r[...]` are the precedents), so a script can report which spec rules have no test.
- A reference layout implied by the sources: lexical grammar (the goianês-to-JS keyword table as data), syntactic grammar, desugaring semantics to JavaScript, a diagnostics catalog with stable codes, the built-in method surface, and a versions appendix tagging every feature with the version that introduced it (Go-style markers).
- Borrow Go's "unspecified behavior" carve-out explicitly: declare exact emitted-JS formatting and diagnostic wording unspecified, while internal golden tests still lock them (changes then require a reviewed bless).
- For breaking syntax changes, an opt-in language version (a pragma or `package.json` field, defaulting to latest for new projects) follows the Rust-edition and Go language-version precedents; define up front what counts as breaking (new reserved word, changed emit shape, removed method).
- Deprecation at solo scale can combine PEP 387 and TypeScript: runtime/compile warnings for a fixed window, an escape-hatch flag, a `migrate` command (codemod), removal only at a major version or edition. The concrete window (for example two minor releases) is my choice, not sourced.

### Gaps
- No source retrieved on "semantic versioning for languages" as such (the Semantic Versioning spec was not fetched); the evidence above is by analogy (Go, Rust, Python, TypeScript).
- Did not retrieve guidance on writing a prose language reference beyond the Go spec and Rust Reference structure.
- Rust's own rule for what is allowed to change in an edition was only sampled through the Edition Guide and RFC 2052 summaries.

## Quality gates for TypeScript projects in 2026: tsconfig, linters, formatters, complexity, coverage, budgets, hooks, supply chain, SBOM

### Takeaway
Two 2026 facts reshape the toolchain: TypeScript 7.0 (native Go port, 2026-07-08) ships without a JavaScript API until 7.1, so typescript-eslint (peer range `<6.1.0`) must stay on TypeScript 6 side by side, while oxlint's type-aware mode runs on typescript-go directly. ESLint 10 is flat-config only, and Node/tool floors have moved to Node 22+. Supply-chain defaults (pnpm 11 release-age and script blocking, Dependabot/Renovate cooldowns, pinned actions) are now first-class quality gates.

## Release engineering for npm packages in 2026: Changesets vs release-please vs semantic-release, trusted publishing, ESM/CJS, exports, CLI, VS Code extensions

### Takeaway
npm trusted publishing (OIDC) with automatic provenance is the 2026 default for CI publishing, and npm's new staged publishing adds a human 2FA approval step that suits a language whose syntax is its API. ESM-only is now low-risk because Node 22.12+ can `require()` ESM. Changesets (explicit human-written release intent) and release-please (Conventional-Commit driven release PRs) are both viable; VS Code Marketplace publishing needs migration off PATs before 2026-12-01.

### Cited Findings

#### Release orchestration
- Changesets: each change carries a semver bump type plus changelog text; "we flatten the version bumps into one single bump at the highest semver range"; change files are committed to the filesystem rather than stored in git; "designed for mono-repos first"; it offers only major/minor/patch bump types and pushes change detail into the changeset text, whereas semantic-release converts commit types (bug-fix, feature) into semver — [Changesets decisions (GitHub copy, flagged "outdated")](https://github.com/changesets/changesets/blob/main/docs/decisions.md); the current docs repeat the flattening rule — [changesets.dev](https://changesets.dev/guide/technical-decisions)
- Contradiction inside Changesets docs: the old decisions page says a peer-dependency change releases the dependent as `major`, while 3.0.0 notes say "Peer dependencies now bump packages that depend on them by `patch` instead of `major`" — [old docs](https://github.com/changesets/changesets/blob/main/docs/decisions.md); [3.0.0 notes](https://github.com/changesets/changesets/releases/tag/%40changesets%2Fcli%403.0.0)
- `@changesets/cli` 3.0.x (3.0.3 on 2026-09-14): Node `^22.11 || ^24 || >=26`, published as ESM, Yarn Classic removed, `changeset tag` renamed `changeset git-tag`, private packages no longer versioned by default, `prettier` option replaced by `format`; new `changeset pack --out-dir` (writes publishable tarballs plus a `publish-plan.json`), `changeset publish --from-pack-dir <dir>` and `changeset publish-plan` — [Changesets 3.0.0 notes](https://github.com/changesets/changesets/releases/tag/%40changesets%2Fcli%403.0.0)
- `changesets/action` v2.1.2 versions packages and opens or updates a "Version Packages" PR; with trusted publishing it recommends the individual sub-actions "to tighten publish permissions", needs `id-token: write` and `pull-requests: write`, and the repo setting "Allow GitHub Actions to create and approve pull requests" — [changesets/action README](https://github.com/changesets/action/blob/main/README.md)
- release-please (17.11.2, 2026-08-24; Node >=22) parses Conventional Commits and maintains Release PRs that update the changelog and version, tag and create a GitHub Release when merged; it "does not handle publication to package managers"; squash-merge is "highly recommend[ed]"; `feat:` = minor, `fix:` = patch, `!` = major — [release-please README](https://github.com/googleapis/release-please/blob/main/README.md)
- semantic-release (25.0.9, 2026-08-05; v25 needs Node >=22.14 and uses npm 11 for publishing) "automates the whole package release workflow", including version, notes and publish — [README](https://github.com/semantic-release/semantic-release/blob/master/README.md); [v25.0.0 notes](https://github.com/semantic-release/semantic-release/releases/tag/v25.0.0); its npm plugin recommends trusted publishing and notes provenance is then automatic — [@semantic-release/npm](https://github.com/semantic-release/npm/blob/master/README.md)

#### Trusted publishing, provenance and staged publishing
- npm trusted publishing uses OIDC instead of long-lived tokens; it requires npm CLI >= 11.5.1 and Node >= 22.14.0; supported: GitHub Actions (GitHub-hosted runners), GitLab CI/CD (shared runners) and CircleCI cloud; self-hosted runners are not supported — [npm trusted publishers](https://docs.npmjs.com/trusted-publishers)
- GitHub setup fields: organization/user, repository, workflow filename (file name only, under `.github/workflows/`), optional environment, and "allowed actions"; up to 10 trusted publishers per package; a configuration cannot be edited (delete and recreate) and must complete its first successful publish within 2 days or it expires — [npm trusted publishers](https://docs.npmjs.com/trusted-publishers)
- `npm stage publish` is always allowed for a trusted publisher; direct `npm publish` and dist-tag management are separate, independent permissions; publishers created after 2026-09-03 default to stage-publish only, those created before 2026-05-20 allow `npm publish` only — [npm trusted publishers](https://docs.npmjs.com/trusted-publishers)
- Docs recommend restricting package access to "Require two-factor authentication and disallow tokens" and, for the "maximum security posture", stage-only permissions so every CI publish waits for a maintainer's 2FA approval; example workflow uses `permissions: id-token: write`, Node 24, `registry-url`, and `package-manager-cache: false  # never use caching in release builds` — [npm trusted publishers](https://docs.npmjs.com/trusted-publishers)
- Provenance is generated automatically for trusted publishing from GitHub Actions or GitLab CI/CD when both repository and package are public; not for CircleCI; disable with `provenance=false` — [npm trusted publishers](https://docs.npmjs.com/trusted-publishers); provenance combines a provenance attestation (source and build instructions) and a registry-generated publish attestation signed via Sigstore — [Generating provenance statements](https://docs.npmjs.com/generating-provenance-statements)
- Staged publishing (npm CLI >= 11.15.0, Node >= 22.14.0): `npm stage publish` uploads to a staging area without 2FA; `npm stage list/view/download` inspect; `npm stage approve <stage-id>` publishes after a 2FA prompt (CLI or npmjs.com "Staged Packages" tab); a new package gets a public placeholder version `0.0.0-stage` until approval — [Staged publishing](https://docs.npmjs.com/staged-publishing); pnpm 11.3+ wraps it as `pnpm stage` and notes staged versions "are not resolved by `pnpm install` until they are explicitly approved" — [pnpm stage](https://github.com/pnpm/pnpm.io/blob/main/docs/cli/stage.md)
- Rationale: the Shai-Hulud worm (notified 2025-09-14) spread through compromised maintainer accounts using malicious post-install scripts; GitHub removed 500+ packages and planned tokens with 7-day lifetimes, deprecation of classic tokens and TOTP 2FA, and "disallow tokens" by default; trusted publishing was added to PyPI (April 2023), RubyGems (December 2023), crates.io (July 2025), npm (also July 2025) and NuGet (September 2025) — [GitHub blog](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/); OIDC trusted publishing was announced generally available on 2025-07-31 — [GitHub changelog](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/)
- pnpm 11 publishes natively (`publish`, `login`, `dist-tag`, `version` no longer delegate to npm); under trusted publishing "pnpm attaches provenance to a public package from a public repository on its own"; `workspace:` ranges are converted to real versions at publish — [pnpm 11.0.0 notes](https://github.com/pnpm/pnpm/releases/tag/v11.0.0); [pnpm publish](https://github.com/pnpm/pnpm.io/blob/main/docs/cli/publish.md); [pnpm workspaces](https://github.com/pnpm/pnpm.io/blob/main/docs/workspaces.md)

#### Module format, exports, build tools and package validation
- Node loads ESM through `require()` when the graph has no top-level await; unflagged since v22.12.0/v20.19.0, and "no longer experimental" in v24.15.0/v25.4.0; the namespace object is returned, `'module.exports'` interop export is supported — [Node modules docs](https://github.com/nodejs/node/blob/main/doc/api/modules.md)
- `"exports"` encapsulates a package ("preventing any other entry points besides those defined in `"exports"`") and supports subpaths and conditional exports — [Node packages docs](https://github.com/nodejs/node/blob/main/doc/api/packages.md)
- Pure-ESM guidance (Sindre Sorhus): option 4 notes Node 22+ may `require()` ESM, but "I strongly recommend moving to ESM instead" — [Pure ESM package](https://gist.github.com/sindresorhus/a39789f98801d908bbc7ff3ecc99d99c); Changesets 3 ("published as ES module") and pnpm 11 ("pure ESM") follow the same direction — [Changesets 3.0.0](https://github.com/changesets/changesets/releases/tag/%40changesets%2Fcli%403.0.0); [pnpm 11.0.0](https://github.com/pnpm/pnpm/releases/tag/v11.0.0)
- attw flags packaging problems such as "Masquerading as CJS", "Resolution failed", "Used fallback condition" — [attw](https://github.com/arethetypeswrong/arethetypeswrong.github.io); build-tool status: tsdown 0.23.1 is the recommended successor to unmaintained tsup — [tsup README](https://github.com/egoist/tsup/blob/main/README.md); [registry](https://registry.npmjs.org/tsdown)

#### CLI packaging
- Node refuses to run TypeScript from `node_modules`, so a published CLI must ship JS (and `.d.ts` for library entries) — [Node TypeScript docs](https://github.com/nodejs/node/blob/main/doc/api/typescript.md)
- pnpm 11 adds `pnpm pack-app`, which packs a CommonJS entry into a standalone executable using Node.js Single Executable Applications — [pnpm 11.0.0 notes](https://github.com/pnpm/pnpm/releases/tag/v11.0.0)

## Decision records and change process: ADR formats, a lightweight RFC process, keeping docs and AI-agent rule files in sync

### Takeaway
ADRs (Nygard, MADR) record context, decision and consequences in short numbered files; Rust RFCs and TC39 stages show how to gate language changes on spec text, tests and review. Scaled to a solo maintainer, the useful parts are a "substantial change" trigger, staged status, tests-before-acceptance and an independent reviewer. Instruction files stay trustworthy only when short, scoped, deterministic where it matters (hooks) and checked against the code by CI.

### Cited Findings

#### ADR formats
- Nygard (2011): keep "records for 'architecturally significant' decisions"; short Markdown files `doc/arch/adr-NNN.md`, "numbered sequentially and monotonically" (numbers never reused); reversed decisions are kept and marked superseded; sections Title (short noun phrase), Context, Decision ("We will ..."), Status (proposed/accepted/superseded), Consequences — [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- MADR 4.0.0 (2024-09-17) full template: YAML front matter (`status`, `date`, `decision-makers`, `consulted`, `informed`), then Context and Problem Statement, Decision Drivers, Considered Options, Decision Outcome (with Consequences and a "Confirmation" section on how compliance is verified, for example an automated fitness function), Pros and Cons of the Options, More Information — [MADR template](https://github.com/adr/madr/blob/main/template/adr-template.md); a minimal variant keeps only context, options, outcome and consequences — [MADR minimal](https://github.com/adr/madr/blob/main/template/adr-template-minimal.md)
- Tooling is lightly maintained: `adr-tools` (last push 2024-04-25) and `@log4brains/cli` 1.1.0 (2024-12-17) — [adr-tools](https://github.com/npryce/adr-tools); [registry](https://registry.npmjs.org/@log4brains/cli)

#### RFC and stage-gated language change processes
- Rust: a "substantial" change (any non-bugfix semantic or syntactic change, removing language features, large `std` additions) needs an RFC; exempt are rephrasings and refactors ("changing shape does not change meaning"), strictly objective quality improvements, and changes invisible to users — [Rust RFCs README](https://github.com/rust-lang/rfcs/blob/master/README.md)
- Rust process: copy `0000-template.md` to `text/0000-my-feature.md`, open a PR, sub-team discusses in the thread, a member proposes a "motion for final comment period (FCP)" with a disposition (merge, close, postpone); "do not squash or rebase commits after they are visible on the pull request" — [Rust RFCs README](https://github.com/rust-lang/rfcs/blob/master/README.md)
- Rust RFC template sections: Summary, Motivation, Guide-level explanation, Reference-level explanation, Drawbacks, Rationale and alternatives, Prior art, Unresolved questions, Future possibilities — [template](https://github.com/rust-lang/rfcs/blob/master/0000-template.md)
- TC39 stages: Stage 1 needs a champion, problem prose and a public repo; Stage 2 a preferred solution with draft spec text and optional polyfills; Stage 2.7 complete spec text with reviewers' and editors' sign-off, whose purpose includes to "Validate the design of the feature through the development of a rigorous and comprehensive test suite"; Stage 3 "sufficient testing and appropriate pre-implementation experience"; Stage 4 two passing implementations and an integrated spec PR; designated reviewers "should not be authors of the spec text" and are chosen by the committee, not the champion — [TC39 process](https://tc39.es/process-document/)

#### Keeping documentation and agent rule files in sync with code
- Claude Code treats CLAUDE.md as context, "not enforced configuration"; "To block an action regardless of what Claude decides, use a PreToolUse hook instead"; specific, concise instructions are followed more consistently; target "under 200 lines per CLAUDE.md file", moving part-of-codebase instructions into path-scoped rules; contradictory instructions may be resolved arbitrarily; auto memory loads only the first 200 lines or 25KB — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- `/doctor prompt-audit` checks instruction files for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other" and changes nothing until asked — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Claude Code can read AGENTS.md as project instructions (v2.1.277+) but by default only when no CLAUDE.md exists in or above the working directory; a CLAUDE.md that imports AGENTS.md loads both; a setting can load both — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- AGENTS.md is "a simple, open format for guiding coding agents", "used by over 60k open-source projects", plain Markdown with no required headings, nested files for monorepos where the nearest file wins, and is stewarded by the Agentic AI Foundation under the Linux Foundation — [agents.md](https://agents.md/)
- Docs-as-tests precedents: rustc tests its books' code examples with `rustdoc --test` and runs a link checker in CI — [tests intro](https://github.com/rust-lang/rustc-dev-guide/blob/master/src/tests/intro.md)
- AI-contribution policies are now explicit: TypeScript's CONTRIBUTING states "We do not accept, under any circumstances, bulk, agent-driven contributions" and accepts a PR only when a specific human operator chose the issue and "intends to shepherd the change through review themselves" — [TypeScript CONTRIBUTING](https://github.com/microsoft/TypeScript/blob/main/CONTRIBUTING.md); typescript-eslint's issue form asks reporters to confirm they followed its AI Contribution Policy — [issue 12518](https://github.com/typescript-eslint/typescript-eslint/issues/12518)

#### Local baseline (repository, verified 2026-10-13)
- The repo's CLAUDE.md still documents `gs-balaio` and `gs-fuçá` as CLIs, but `packages/core/package.json` exposes only `goiasscript` and `goias`, `packages/core/bin/` contains only those two scripts, and `KEEP-OR-ARCHIVE.md` lists `bin/gs-balaio.js` and `bin/gs-fuça.js` under its section "ARCHIVE — preservado em archive/v2-experimental, removido do v1.5"; this is a concrete docs-versus-code drift — [local: CLAUDE.md](<repo>/CLAUDE.md); [local: core package.json](<repo>/packages/core/package.json); [local: KEEP-OR-ARCHIVE.md](<repo>/KEEP-OR-ARCHIVE.md)
- The user's agent set already includes a read-only, fresh-context adversarial `plan-reviewer` for plans and diffs — regras globais do dono (agents.md)

### Inferences
- Use two lightweight artifacts under `docs/`: ADRs (MADR minimal plus a "Confirmation" line naming the CI check that enforces the decision) for architecture and tooling choices, and RFCs only for "substantial" language changes (syntax, semantics, keyword table, diagnostic codes, removals), adapted from Rust's trigger list. Refactors, internal changes and perf work need no RFC.
- Scale TC39 stages to a status field: Draft (problem and examples) to Proposed (EBNF delta, goianês-to-JS examples, migration notes) to Accepted (conformance tests written and failing) to Implemented (tests green, docs and spec updated) to Released; deprecated and removed as terminal states. This mirrors Stage 2.7's test-first intent and Stage 4's "tests pass" gate.
- A solo maintainer has no second reviewer; the closest substitute for TC39's "reviewers who are not the author" is the existing fresh-context `plan-reviewer` agent run against the RFC before acceptance (my suggestion, not a sourced practice). Rust's FCP window has no direct solo analogue.
- Keep one canonical instruction file: either AGENTS.md as the neutral source with a thin CLAUDE.md that imports it, or CLAUDE.md alone, under 200 lines, with language-specific rules path-scoped. Deterministic requirements (identifiers in English, commit format, no `any`) belong in hooks, not prose. Add CI checks that execute every fenced goianês code block in docs and README, run a link checker, and assert that every CLI command named in docs resolves to a `bin` entry or `--help` output (the `gs-balaio` drift would have been caught).
- Add an AI-contribution policy to CONTRIBUTING.md before accepting external PRs, modeled on TypeScript's and typescript-eslint's.

### Gaps
- No source found on RFC processes explicitly sized for single-maintainer projects; the scaled-down process above is extrapolation.
- ADR adoption evidence for TypeScript/Node projects specifically (versus the generic templates) was not collected.
- Did not retrieve evidence on how well agents follow AGENTS.md versus CLAUDE.md in practice, only the loading rules.

## Monorepo practices with pnpm workspaces: Turborepo/Nx vs plain `pnpm -r`, CI caching

### Takeaway
pnpm workspaces already provide topological recursion, filtering by dependency graph or git diff, the `workspace:` and `catalog:` protocols, and publish-time version rewriting. Turborepo and Nx add task-output caching and affected-only execution, which pay off at larger task counts; with one library and three apps, plain `pnpm` plus CI dependency caching is the low-complexity choice until CI time becomes a problem.

### Cited Findings
- `pnpm -r` runs scripts in topological order ("dependencies run before their dependents"), with `--no-sort`, `--parallel` and `--workspace-concurrency` to change it — [pnpm recursive](https://github.com/pnpm/pnpm.io/blob/main/docs/cli/recursive.md)
- Filtering: `--filter <pkg>...` (package plus dependencies), `--filter "...<pkg>"` (plus dependents), directory selectors combined with `[<since>]`, e.g. `pnpm --filter "{packages/**}[origin/master]" <cmd>` selects changed packages — [pnpm filtering](https://github.com/pnpm/pnpm.io/blob/main/docs/filtering.md)
- The `workspace:` protocol (`workspace:*`, `~`, `^`) pins local packages and is replaced by the real version when publishing — [pnpm workspaces](https://github.com/pnpm/pnpm.io/blob/main/docs/workspaces.md); "Catalogs" define shared version ranges as constants referenced with `catalog:` in `package.json` — [pnpm catalogs](https://github.com/pnpm/pnpm.io/blob/main/docs/catalogs.md)
- pnpm 11: Node 22+ required, new `pnpm ci`, `pnpm sbom`, `pnpm clean`; `.npmrc` is auth/registry only, so settings live in `pnpm-workspace.yaml` — [pnpm 11.0.0 notes](https://github.com/pnpm/pnpm/releases/tag/v11.0.0)
- Turborepo 2.11.8 (2026-10-13): caches task outputs keyed by an input hash in `.turbo/cache`, assumes tasks are deterministic, can share a Remote Cache (default: Vercel Remote Cache "with zero configuration"), and `turbo run build lint test --affected` defaults to `--filter=...[main...HEAD]` and needs enough git history (for example a checkout with `--filter=blob:none --depth=0`) — [Turborepo docs](https://turborepo.com/docs); [caching](https://turborepo.com/docs/crafting-your-repository/caching); [run reference](https://turborepo.com/docs/reference/run); [registry](https://registry.npmjs.org/turbo)
- Turborepo's own pitch targets scale: "A single monorepo might have thousands of tasks to execute" — [Turborepo docs](https://turborepo.com/docs)
- Nx 23.3.0 (2026-10-07) documents task caching, affected-task runs and distributed execution (Nx Agents) — [Nx intro](https://nx.dev/getting-started/intro); [registry](https://registry.npmjs.org/nx)
- CI caching: `actions/setup-node` caches pnpm only via the explicit `cache: 'pnpm'` input; automatic caching is npm-only, and privileged/release workflows should disable it (`package-manager-cache: false`) — [setup-node README](https://github.com/actions/setup-node/blob/main/README.md); npm's trusted-publishing example repeats "never use caching in release builds" — [npm trusted publishers](https://docs.npmjs.com/trusted-publishers)
- TypeScript 7 project-reference builds can run in parallel (`--builders`), multiplied by `--checkers`, so memory scales with both — [TS 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)

### Inferences
- With one compiler package and three apps, plain `pnpm -r`/`--filter` plus `setup-node`'s pnpm cache covers the need; adding Turborepo or Nx now would add configuration and a cache-correctness assumption (deterministic tasks) without evidence of a CI-time problem. Revisit when CI exceeds an acceptable duration or the package count grows; Turborepo's `--affected` is the likeliest first step, and the user already has Vercel in the toolchain for its default Remote Cache (not verified as a fit).
- Use `catalog:` for shared dev-tool versions (TypeScript, Vitest, ESLint) so the TypeScript 6-pin and later TS 7 switch is a one-line change, and `workspace:*` between packages with publish-time rewriting handled by pnpm or Changesets.
- Order of CI jobs follows from the sources: install with a frozen lockfile and pnpm cache, typecheck and lint, tests with coverage, mutation testing (incremental on PRs), package validation (attw/publint on the packed tarball), then a separate release workflow with no cache and `id-token: write`.

### Gaps
- No source retrieved on incremental caches for `tsc` (`.tsbuildinfo`), ESLint (`--cache`) or Vitest in CI.
- Nx documentation fetched only as navigation text; its feature claims above rest on section titles.
- No measurements of this repository's CI duration, so the "plain pnpm is enough" conclusion is an inference from scale, not data.
- Remote-cache alternatives to Vercel's and their security trade-offs were not researched.
