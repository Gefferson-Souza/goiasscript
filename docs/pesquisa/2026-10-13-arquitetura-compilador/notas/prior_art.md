## 1. wenyan-lang: compiler architecture, stdlib, playground/IDE, packaging, maintenance trajectory

### Takeaway
Wenyan is a hand-written, multi-pass TypeScript compiler (quote-aware macro pass, character-level tokenizer, flat "abstract syntax chain", optional type checking, three emitters for JS/Python/Ruby) whose standard library is itself written in Wenyan. It combined a launch-week viral concept with an online IDE and npm/CLI packaging, but master has had no commits since January 2023 and its editor tooling came mostly from third parties.

### Cited Findings
**Compiler architecture**
- Source is TypeScript under `src/`: `parser.ts` (815 lines, holds tokenizer, parser and `compile()`), `reader.ts` (imports), `macro.ts`, `keywords.ts`, `typecheck.ts` (709 lines), `render.ts`, `stdlib.ts`, `execute.ts`, `converts/hanzi2num.ts` (917 lines), `transpilers/{base,index,js,py,rb}.ts` — [GitHub tree API](https://api.github.com/repos/wenyan-lang/wenyan/git/trees/master?recursive=1); [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts)
- `compile(txt, options)` runs labelled passes: "[PASS 0] EXPAND-MACROS", "[PASS 1] TOKENIZER", optional identifier romanization, "[PASS 2] ABSTRACT SYNTAX CHAIN", "[PASS 2.5] TYPECHECK" only when `strict` is set, then "[PASS 3] COMPILER" which selects `transpilers[lang]` (`lang` defaults to "js") — [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts)
- The tokenizer `wy2tokens` is a hand-written character loop with state flags (identifier, number, literal nesting level, data); tokens are tuples `[TokenType, value, position]`; the characters `。、`, newlines, tabs and spaces are ignored (`IGNORE_SYMBOLS`) — [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts); [types.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/types.ts). The README confirms "Punctuations and newlines are completely optional" — [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md)
- Classical Chinese has no spaces between words, so the creator resolves ambiguity by matching the longest keyword first, then shorter ones (summarized) — [IEEE Spectrum](https://spectrum.ieee.org/classical-chinese)
- Keywords are a lookup table from surface form to `[TokenType, subtype]` (e.g. 吾有 maps to decl/uninit, 書之 to print, 名之曰 to name); number literals use a Chinese-numeral alphabet (`NUMBER_KEYWORDS`) plus a 917-line hanzi-to-number converter — [keywords.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/keywords.ts); [hanzi2num.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/converts/hanzi2num.ts)
- A textual macro pass (`extractMacros` / `expandMacros`) runs before tokenizing; its scanner tracks quote nesting (「」 = level 1, 『』 = level 2) and only matches directives outside quotes; imports use the keyword 吾嘗觀 — [macro.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/macro.ts)
- Identifiers are delimited by 「」 and strings by 「「 」」 in the README example (`名之曰「甲」`, `曰「「問天地好在。」」`), i.e. identifiers are explicitly quoted — [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md)
- `CompileOptions` include `romanizeIdentifiers: "none" | "pinyin" | "unicode" | "baxter"`; pinyin and Baxter romanization maps ship in `src/converts/` and `tokenRomanize` runs when the option is not "none" — [types.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/types.ts); [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts). The stated reason is not in the files I read.
- `typecheck.ts` is a type checker whose result is printed as signatures (type variables shown as `'a`, plus `(…) arr` and `->`); it is invoked only in `strict` mode — [typecheck.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/typecheck.ts); [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts)
- Syntax errors are produced by an `assert` helper that prints "[Syntax Error] <msg>" followed by "Line N, Character M:" and the source line — [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts)
- `BaseTranspiler` takes `asc: ASCNode[]` (a flat node array), owns temp-variable counters (`_ans1`, `_rand1`) and wraps modules with `/*___wenyan_module_..._start___*/` markers; concrete emitters are JS (308 lines), Python and Ruby; README: "Compiles to JavaScript, Python, or Ruby" — [base.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/transpilers/base.ts); [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md)
- `reader.ts` bundles imports; an HTTP import is refused unless the `allowHttp` option is set or the host is in `trustedHosts` (default trusted host: `raw.githubusercontent.com/wenyan-lang/wenyan/master`), and a FIXME admits the prefix check can be bypassed by relative path resolution — [reader.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/reader.ts); [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts)
- The standard library is Wenyan source: `stdlib.ts` loads `lib/**/*.wy` through webpack `require.context`; `lib/` holds shared modules (e.g. 算經, 列經, 易經, 曆法) plus per-target folders `lib/js`, `lib/py`, `lib/rb` — [stdlib.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/stdlib.ts); [tree API](https://api.github.com/repos/wenyan-lang/wenyan/git/trees/master?recursive=1)
- `render.ts` (336 lines) renders programs as book-style pages (it defines a CJK serif font and red/black colours and exports `render` and `unrender(svgs)`); IEEE describes a renderer that displays programs "in a style resembling pages from ancient Chinese texts" — [render.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/render.ts); [IEEE Spectrum](https://spectrum.ieee.org/classical-chinese)
- Tests are Jest: `test/examples.test.ts` with a snapshot file, plus `numbers`, `import`, `reader` and `stdlib.*` tests; `examples/` holds 46 files — [tree API](https://api.github.com/repos/wenyan-lang/wenyan/git/trees/master?recursive=1)
- The localization paper notes Wenyan mandates the character 者 at the end of an `if` statement to stay close to Classical Chinese — [Swidan & Hermans, SPLASH-E 2023](https://doi.org/10.1145/3622780.3623645)

**Tooling and packaging**
- Published on npm as `@wenyan/core` (works in Node and browsers; an unpkg bundle exposes `Wenyan.compile`) and `@wenyan/cli`; the wiki warns the API "might be changed frequently" — [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md); [wiki: Compiler-API](https://github.com/wenyan-lang/wenyan/wiki/Compiler-API)
- The online IDE (ide.wy-lang.org) was moved to its own repo in v0.3.2; that repo is a static site (`static/assets/js/ide.js`, `storage.js`, `show-invisibles.js`, a service worker `sw.js`) whose `package.json` lists only dev tooling (`live-server`, `nodemon`, `concurrently`, `fast-glob`) — [CHANGELOG](https://github.com/wenyan-lang/wenyan/blob/master/CHANGELOG.md); [wenyan-lang/ide](https://github.com/wenyan-lang/ide)
- A package manager `wyg` (文淵閣) and a registry exist: `wyg` 43 stars (last push 2023-01-05), `wyg-registry` 8 stars (2024-04-04); other org repos: `book` (379 stars, an introductory book), `highlight` (7), `ide` (26), `snippets`, `loader` (Webpack loader), `rollup-plugin` — [org repos API](https://api.github.com/orgs/wenyan-lang/repos)
- The `highlight` repo derives editor highlighters from the compiler's own keyword table: `scripts/keywords.js` requires `@wenyan/core`, iterates `Wenyan.KEYWORDS` to sort keywords into groups, and defines the string delimiters; `build-cm.js`, `build-prism.js` and `build-tm.js` consume it to produce CodeMirror, Prism and TextMate highlighters — [keywords.js](https://github.com/wenyan-lang/highlight/blob/HEAD/scripts/keywords.js); [build-tm.js](https://github.com/wenyan-lang/highlight/blob/HEAD/scripts/build-tm.js)
- Editor and extra tooling came from third parties: VS Code plugin (antfu), Vim (voldikss), Sublime (absop), a JS-to-Wenyan decompiler "wenyanizer" (zxch3n), a JVM compiler (MagicLu550) — [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md)
- Contribution paths advertised: share scripts on a snippets site, add examples, publish packages on wyg; "open an issue first" for code changes — [wiki: Contributing](https://github.com/wenyan-lang/wenyan/wiki/Contributing)

**Community and maintenance trajectory**

### Inferences
- Wenyan's pipeline (quote-aware macro pre-pass, tokenizer, flat node list, per-target emitters behind a base class) is the smallest "real compiler" template found and maps directly onto a transpile-to-JS dialect.
- Explicit identifier delimiters (「」) remove keyword/identifier collisions at the lexical level; GoiásScript has no such delimiter, so it must solve collisions another way (see section 5).
- Deriving highlighters from the compiler's own keyword table (Wenyan `highlight`; the same idea appears in EsJS, section 3) keeps editor support in sync with the language at near-zero maintenance cost.
- Writing the stdlib in the language itself with small per-target shims keeps the host-language surface small.
- Launch virality (concept + online IDE + README) did not translate into sustained maintenance; the package manager has tiny adoption relative to the main repo's stars (stars are only a weak proxy for usage).
- Dormancy since 2023 is inferred from commit dates; no maintainer statement was found.

### Gaps
- No official statement on project status; not verified whether work continues outside master.
- `tokens2asc` (the actual grammar logic) was not read in depth.
- npm download counts for `@wenyan/core` were not retrieved.
- Guinness page not opened (snippet only). Citrine (a localization-first language mentioned in the HN thread) was not researched.

## 2. Hedy: grammar approach (Lark), keyword localization, beginner-friendly errors, research findings

### Takeaway
Hedy (active as of 2026-10) is a gradual language implemented with Lark grammars that exist per level and per locale ("total" grammars built by concatenation), transpiled to Python on the server and run in the browser with Skulpt; its grammars deliberately accept more than the language allows so the parser can emit targeted errors. Research (Hermans et al.) shows a low error rate, strong learner demand for better error messages and localized keywords, and unresolved issues around word order, diacritics and mixing languages.

### Cited Findings
**Grammar and architecture**
- Original design (ICER 2020): implemented in Python with Lark; code is parsed and then transpiled to Python, "for example by adding brackets where needed"; the web version needs no install, which the author expects to boost adoption in schools where teachers cannot install software, and it works on phones and tablets — [Hermans, ICER 2020](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf); [DOI](https://doi.org/10.1145/3372782.3406262)
- Level 1 grammar parses more than the language allows: besides `print`, `ask`, `echo`, a fallback rule `textwithoutspaces " " text -> invalid` lets `show hello world` parse so the system can answer "show is not a command in Hedy. Did you mean print?" — [ICER 2020](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- The current grammar keeps this idea: `error_invalid.-100: textwithoutspaces text?` with a comment that priority -100 makes ambiguity resolution consider it last; it also has `error_invalid_space` — [level1.en-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level1.en-Total.lark)
- Current architecture (wiki): Hedy code is transpiled server-side using Lark (parse to AST, `IsValid()` check, transform to Python); the Python runs in the browser with Skulpt; on errors the transpiler retries allowing "invalid" code to be skipped and maps errors back with a source-mapper ("skipping faulty code") — [Hedy Architecture wiki](https://github.com/hedyorg/hedy/wiki/Hedy-Architecture)
- The wiki says the transpiler logic "resides in hedy.py", but no `hedy.py` exists in the main repo's current file tree (only `hedyweb.py`); `requirements-prod.txt` pins `hedylang==0.0.8` ("The version of github.com/hedyorg/hedylang") and `lark==1.1.9`, and the `hedyorg/hedylang` repo description says "This repository contains the language tooling" — [wiki](https://github.com/hedyorg/hedy/wiki/Hedy-Architecture); [tree API](https://api.github.com/repos/hedyorg/hedy/git/trees/HEAD?recursive=1); [requirements-prod.txt](https://github.com/hedyorg/hedy/blob/HEAD/requirements-prod.txt); [hedylang repo](https://api.github.com/repos/hedyorg/hedylang)
- Levels x locales: one reference grammar split into per-level files (about 300 LOC); Lark lacks modularity, so the compiler concatenates files for consecutive levels and does rudimentary rewriting to override/deprecate constructs; each locale is a Lark file of keyword nonterminals (about 800 LOC) prepended to the level files; result: over 380 "total" grammars, 48,664 LOC; at the time, 19 levels and keywords for 19 languages — [van der Storm & Hermans, SLE 2022 "Gradual Grammars"](https://homepages.cwi.nl/~storm/publications/gradual-grammars.pdf)
- The repo checks in 16 such files as `grammars-Total/levelN.<lang>-Total.lark`, mostly `en` with `nl` variants for levels 8 and 13 — [grammars-Total](https://github.com/hedyorg/hedy/tree/HEAD/grammars-Total)
- Keyword terminals accept the localized spelling and the English one: Dutch `_DEFINE: ("definieer" | "define")`, `_CALL: ("roep" | "call")`; free-text rules stop at keywords of both languages through negative lookahead, e.g. `(?!anders|else)` and `(?!to|toe aan|from|uit)` — [level8.nl-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level8.nl-Total.lark); [level13.nl-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level13.nl-Total.lark)
- Locale-aware punctuation and script edge cases appear in the grammar: list separators include Arabic comma `،`, fullwidth comma `，` and ideographic comma `、`; the `text` rule refuses to start with an Arabic tatweel so `قولـــ` is not parsed as printing "___" (issue #2699) — [level1.en-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level1.en-Total.lark); [level8.nl-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level8.nl-Total.lark)
- Fabric (the SLE 2022 formalism) separates "vertical" graduality (levels) from "horizontal" internationalization (keyword renaming and sentence reordering); the authors state the ad hoc token-definition approach works for keyword translation but does not allow changing sentence order or inserting/removing keywords — [Gradual Grammars](https://homepages.cwi.nl/~storm/publications/gradual-grammars.pdf)
- Editor highlighting uses Lezer grammars per level (`highlighting/lezer-grammars/level1..16.grammar`) with helper scripts (`highlighting/generate-rules-highlighting.py`, `highlighting-trad.json`, `build-tools/heroku/generate-lezer-parsers`) — [highlighting/](https://github.com/hedyorg/hedy/tree/HEAD/highlighting); [build-tools](https://github.com/hedyorg/hedy/tree/HEAD/build-tools)
- The repo also carries formal-semantics experiments in Dafny for levels 1 to 5 and 17 research PDFs/theses — [semantics/](https://github.com/hedyorg/hedy/tree/HEAD/semantics); [content/research](https://github.com/hedyorg/hedy/tree/HEAD/content/research)

**Keyword localization**
- ICER 2020 sees localized keywords as enabled by the simple low-level grammar and states "research has shown that learners learn programming more easily in their own mother tongue", with a gradual switch to English/Python versions — [ICER 2020 section 5.4](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- Keyword choices were made for non-English speakers: `ask` rather than `input` (named for its role, not its action) and `repeat x times` rather than `for`, because `for` sounds like "four" to non-English-native Python novices — [ICER 2020 sections 3.2.1, 3.2.5](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- Discussion #776 (Sep 2021 to Feb 2022) (summarized): translating keywords is not enough (Dutch needs split keywords such as `print hallo allemaal uit`; Japanese and Arabic lack an "is" verb; English "at random" is two words but German "zufällig" is one); mixing languages would be limited to English plus one other language to minimize overlap; a contributor proposed that a new language must not add keywords clashing with English ones unless the meaning is identical; a staged roadmap was listed (translate and parse, translate programs between languages, mix, override grammar) — [Hedy discussion #776](https://github.com/hedyorg/hedy/discussions/776)
- Translation is community-driven through Weblate ("You do not need programming experience or knowledge to translate Hedy"); the repo has a `translations/` tree (78 files); error-message titles are `gettext` keys in `content/error-messages.txt` and Flask-Babel is in the stack — [README](https://github.com/hedyorg/hedy#readme); [error-messages.txt](https://github.com/hedyorg/hedy/blob/HEAD/content/error-messages.txt); [requirements-prod.txt](https://github.com/hedyorg/hedy/blob/HEAD/requirements-prod.txt)
- Scale: Hermans' 2024 invited-talk abstract says Hedy "is available in 54 different languages" and "now serves about 500,000 monthly users" — [ICPEC 2024 abstract](https://drops.dagstuhl.de/storage/01oasics/oasics-vol122-icpec2024/OASIcs.ICPEC.2024.1/OASIcs.ICPEC.2024.1.pdf); Wikipedia's list gives 47 languages as of Sept 2024 (a different date and possibly a different counting rule) — [Wikipedia](https://en.wikipedia.org/wiki/Non-English-based_programming_languages) (summarized)
- A talk summary says right-to-left languages required changes to the website, parser and syntax highlighter (search snippet) — [Joy of Coding 2022](https://joyofcoding.org/2022/speakers/felienne-hermans.html)

**Beginner-friendly errors and research findings**
- Design philosophy: because early grammars are simple, error messages can be precise; example: `prnt Hello World` yields "prnt is not a Hedy level 1 command, did you mean print?", which the author calls arguably more helpful than Python's `NameError`; error complexity can also grow gradually with the levels — [ICER 2020 section 5.5](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- Evaluation: public release 2020-03-16, three weeks of data, 9,714 programs analysed; 1,363 (12.2%) had an error. Error classes: incomplete code 18.6%, code run at the wrong level 18.4%, misspelled or misplaced keyword 17.1%, invalid character 16.1%, invalid spaces 12.5%, quotes 8.1%, multiline command 5.3%; announcements went out via Twitter, a university press release and Dutch news sites — [ICER 2020 sections 6, 7](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- On "invalid characters" the paper notes: "Other invalid characters included letters with accents, or errors due to encoding issues"; it also saw programs using Dutch or Spanish keywords instead of English ones — [ICER 2020 sections 7.3, 7.6](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- User study (39 children aged 11 to 14, six weeks): children like the gradual design and control over difficulty; challenges are that commands change or overlap; suggested improvements are better error messages, less sensitivity to syntax errors and localized keywords; children often did not fully understand error messages and, when reading them aloud, skipped punctuation characters — [Gilsing, Pelay, Hermans 2022](https://doi.org/10.1016/j.cola.2022.101158); [PDF copy in the Hedy repo](https://github.com/hedyorg/hedy/blob/HEAD/content/research/Design_Implementation_and_evaluation_of_the_Hedy_programming_language_2022.pdf)
- Hedy is open source (EUPL-1.2), 1,694 stars, last push 2026-10-10, and the GitHub contributors API paginates to 625 entries (including anonymous) — [GitHub API](https://api.github.com/repos/hedyorg/hedy); [contributors API](https://api.github.com/repos/hedyorg/hedy/contributors?per_page=1&anon=true)
- Hacker News visibility is small (6, 5 and 3 points on the Hedy stories) despite the user base — [HN 38509871](https://news.ycombinator.com/item?id=38509871); [HN 26761487](https://news.ycombinator.com/item?id=26761487)

### Inferences
- "Grammar that over-accepts plus a low-priority catch-all `invalid` rule" is a cheap, reusable way to produce friendly, specific errors in a dialect language.
- Per-locale keyword files prepended to shared grammar files is how Hedy scaled to dozens of locales; the file names suggest (not verified) that highlighter rules are produced from the same grammar/translation data. A single-dialect language gets the same maintenance benefit from one keyword table.
- Mixing policy matters: Hedy restricted mixing to own-language plus English to avoid keyword overlaps; GoiásScript's "English API names stay English" is the same shape of decision.
- The transpiler appears to have moved out of the main repo into the `hedylang` package; this is inferred from the missing `hedy.py` and the pinned dependency, not stated by a source.
- Hedy's evidence base is children, short studies and no control group, so it supports "error messages and localized keywords matter" but not a measured benefit size.

### Gaps
- The script that builds the per-locale grammars was not located in the current main repo (only generated outputs and the paper's description); the `hedylang` code was not read.
- Current level count not verified (13 in the 2020 paper, 19 in the 2022 paper, grammar files to level 16 visible in the repo).
- The right-to-left claim rests on a search snippet; discussion #776 content is from a fetch summary and may paraphrase.
- Hedy research PDFs seen by title only and not read: "Hedy_Community_Content_and_Localisation_2023", "Introducing_the_Gradual_Feedback_Model_2021", "Implementing_skipping_faulty_code_for_the_Hedy_programming_language_2023", "Hedy_De_implementatie_van_een_syntax_highlighter_2021" — [content/research](https://github.com/hedyorg/hedy/tree/HEAD/content/research)
- No controlled study of adults using localized-keyword languages was found.

## 3. Spanish/Portuguese-keyword JS dialects, teaching languages and regional-dialect languages (implementation technique, targets, tooling)

### Takeaway
Portuguese teaching languages (Égua, Delégua, Potigol, Portugol Studio) use real front ends (hand-written lexer/parser or ANTLR); JS-targeting dialects split into token-level tools (EsJS compiler packages, Sweet.js macros in UrduScript) and whole-source regex substitution (Canarinho, Thengascript, bhailangfun), which are all small, low-adoption projects. No established Brazilian regional-dialect language was found; the nearest are BIRL (bodybuilder slang, compiles to C, dormant) and Bhai-lang (Hinglish slang, TypeScript).

### Cited Findings
**Technique summary (as read in source)**

| Project | Technique | Target | Source |
|---|---|---|---|
| Wenyan | quote-aware macro pass, character tokenizer, flat node list, per-target emitters | JS, Python, Ruby | [parser.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/parser.ts) |
| EsJS | `esbabel` package with `lexer.ts` and `generator.ts`; alias plugins per JS built-in; a second compiler variant (`essucrase`) | JavaScript | [tree](https://api.github.com/repos/es-js/esjs/git/trees/HEAD?recursive=1) |
| UrduScript | Sweet.js syntax macros, one exported macro per Urdu keyword | JavaScript | [keywords.js](https://github.com/asadm/urduscript/blob/HEAD/src/keywords.js) |
| Thengascript | one case-insensitive regex alternation of all keys with a quote-skipping lookahead, then `eval` | ECMAScript in the browser | [thengascript.js](https://github.com/makersofkerala/thengascript/blob/HEAD/thengascript.js) |
| Canarinho | one `\b`-anchored global regex per dictionary entry over the whole source; reverse mode by inverting the dictionary | JavaScript | [transpilador.js](https://github.com/canarinho-js/canarinho/blob/HEAD/codigo_fonte/transpilador.js) |
| bhailangfun | chain of `.replace()` regexes, then `eval` | JavaScript | [interpreter.js](https://github.com/tuhinpal/bhailangfun/blob/HEAD/interpreter.js) |

### Inferences
- The implementation spectrum is: full pipeline (Delégua, Égua, Potigol, Portugol Studio, Rockstar, Hedy), token/macro level (EsJS `esbabel`, UrduScript via Sweet.js, ZhPy via pyparsing), and whole-source regex or dictionary substitution (Canarinho, Thengascript, bhailangfun). The regex group consists of small projects (5, 69 and 4 stars); the ecosystems that grew chose tokenizers or parsers.
- EsJS is the closest structural analog to GoiásScript (dialect compiling to JS): keyword table, aliases for built-ins (`consola`/`console`), and generated editor syntax and reserved-words table from the same keyword maps; deriving the dialect's TextMate grammar from the stock JavaScript one is a cheap trick worth reusing.
- Delégua's dual-spelling table is a concrete answer to the accent question for Portuguese; Portugol Studio and Latino chose to avoid accents (keywords and identifiers, respectively).
- A regional-dialect language with serious tooling appears to be an unoccupied niche among Brazilian projects; BIRL is humor-only and dormant. This is an inference from negative search results.
- Delégua's choice to keep heavy backends outside the core is a scope-control pattern (see section 7).

## 4. Viral esolangs (LOLCODE, Rockstar, ArnoldC): what "serious" implementations look like

### Takeaway
All three joke languages sit on serious engineering: a written spec, a real parser (PEG via PEG.js/Pegasus-style grammars or parboiled, or an interpreter in C), and fixture-driven conformance tests. Virality was a launch-day event (Rockstar reached 297 HN points one day after repo creation; ArnoldC 204), while long-term health depended on one maintainer.

### Cited Findings
**LOLCODE**
- Spec 1.2 is marked "FINAL DRAFT — 12 July 2007" and states its goal: a baseline for all later specs; some expected features "may appear 'incomplete'" deliberately because "it will be easier to add to the language than to change and introduce further incompatibilities" — [LOLCODE spec 1.2](https://github.com/justinmeza/lolcode-spec/blob/HEAD/v1.2/lolcode-spec-v1.2.md)
- The spec fixes lexical rules: spaces delimit tokens "although some keyword constructs may include spaces"; a newline ends a command; a comma is a soft command break; `...` continues a line; `BTW` starts a comment; unterminated string literals are errors — [LOLCODE spec 1.2](https://github.com/justinmeza/lolcode-spec/blob/HEAD/v1.2/lolcode-spec-v1.2.md)
- The spec repo archives v1.2 and v1.3 markdown files (635 stars, last push 2023-02-20) — [lolcode-spec](https://api.github.com/repos/justinmeza/lolcode-spec)
- `lci` (C, created 2010, last push 2026-09-11, main author 138 commits among 13 contributors) states it is "correct, portable, fast, and precisely documented", compiles to bytecode (and machine code where types can be pinned), ships unit tests with the source, and tags `v1.3` for the 1.3 spec — [lci README](https://github.com/justinmeza/lci); [repo API](https://api.github.com/repos/justinmeza/lci); [contributors API](https://api.github.com/repos/justinmeza/lci/contributors)

- 6,888 stars, last push 2024-01-31 (GitHub repository search metadata), 11 contributors with the top contributor at 24 commits; HN story 204 points / 38 comments (2014-02-25); a community compiler to JS exists (`arnoldc.js`) — [ArnoldC repo](https://github.com/lhartikk/ArnoldC); [contributors API](https://api.github.com/repos/lhartikk/ArnoldC/contributors); [HN 7299658](https://news.ycombinator.com/item?id=7299658); [arnoldc.js](https://github.com/mattdsteele/arnoldc.js)

### Inferences
- The "serious" recipe is spec, parser generator or hand-written parser, and a fixture suite organized by feature; none of the three relies on regex substitution.
- Rockstar's practice of making docs examples double as tests, keeping v1 fixtures alive, and publishing a "changes from v1" page is directly reusable.
- Virality here comes from a one-line joke with a shareable artifact (stickers, quotable keywords) plus a playground; sustained engineering stayed with one or two people.

- ArnoldC's test suite was not inspected; LOLCODE spec governance (who may amend) is not documented in what I read.

## 5. Design patterns: multi-word keywords, accents, collisions, English API names, error i18n, humor

### Takeaway
Prior art converges on a few patterns: single-lexeme or longest-match tables for multi-word keywords, registering accented and unaccented spellings (or normalizing) for keywords, a reserved-word set or lookahead guards (plus explicit delimiters) to avoid collisions, alias tables for host-API names, gettext-style message catalogs, and plain-language errors with a hint. Whole-source regex substitution fails in specific, reproducible ways on accents, strings, comments and Unicode normalization. Humor in diagnostics is common in joke languages but has no empirical support; the research that exists warns about vocabulary and slang barriers.

### Cited Findings
**Multi-word keywords**
- Wenyan matches the longest keyword first because the script has no spaces — [IEEE Spectrum](https://spectrum.ieee.org/classical-chinese) (summarized)
- LOLCODE: tokens are space-delimited "although some keyword constructs may include spaces" — [LOLCODE spec 1.2](https://github.com/justinmeza/lolcode-spec/blob/HEAD/v1.2/lolcode-spec-v1.2.md)
- ArnoldC keeps phrases such as "BECAUSE I'M GOING TO SAY PLEASE" as whole-string constants in a PEG parser; Bhai-lang defines multi-word token types (`"hi bhai"`, `"jab tak bhai"`); Canarinho's dictionary has space-separated keys (`ou então`, `caso seja`) — [ArnoldParser.scala](https://github.com/lhartikk/ArnoldC/blob/HEAD/src/main/scala/org/arnoldc/ArnoldParser.scala); [bhaiLangSpec.ts](https://github.com/DulLabs/bhai-lang/blob/HEAD/packages/parser/src/constants/bhaiLangSpec.ts); [dicionario.js](https://github.com/canarinho-js/canarinho/blob/HEAD/codigo_fonte/dicionario.js)
- Hedy terminals include a trailing optional space (`"print" _SPACE?`) and discussion #776 notes English "at random" (two words) versus German "zufällig" (one word) — [level1.en-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level1.en-Total.lark); [discussion #776](https://github.com/hedyorg/hedy/discussions/776) (summarized)
- Keyword choice for non-native speakers: avoid homophones (`for` sounds like "four") and name keywords by role (`ask`, not `input`) — [ICER 2020](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)

**Accents, diacritics and Unicode**
- The localization framework (12 aspects, applied to 13 languages) has a "Diacritics" section: if a keyword is translated with accents, do we also accept the unaccented form ("If répète 3 fois is the correct code, do we also allow repete 3 fois or will that lead to an error message?"), and is a name with and without accents the same variable ("diacritic sensitivity", like case sensitivity)? It adds that most languages supporting non-Latin variable names are diacritic sensitive, probably as a tooling accident, and flags this as especially relevant for teaching languages — [Swidan & Hermans, SPLASH-E 2023](https://doi.org/10.1145/3622780.3623645)
- Same paper: compilers often assume identifiers use Latin a to z; some languages restrict comment characters; the framework also lists numerals, "characters without meaning" (Arabic tatweel), localized punctuation, right-to-left, alternative keywords (Ebda3 accepts both Arabic forms of "to"), multilingual programming and error messages — [SPLASH-E 2023](https://doi.org/10.1145/3622780.3623645)
- Three policies seen in Portuguese/Spanish languages: Delégua accepts both spellings through duplicate table entries; Portugol Studio's lexer uses only unaccented keywords; Latino rejects accented letters and `ñ` in identifiers — [palavras-reservadas.ts](https://github.com/DesignLiquido/delegua/blob/HEAD/fontes/lexador/palavras-reservadas.ts); [PortugolLexico.g4](https://github.com/UNIVALI-LITE/Portugol-Studio/blob/HEAD/core/src/main/antlr/PortugolLexico.g4); [Latino README](https://github.com/lenguaje-latino/latino)
- Canarinho defines accented keywords (`função`, `variável`, `senão`) and matches them with `\b`-anchored regexes — [dicionario.js](https://github.com/canarinho-js/canarinho/blob/HEAD/codigo_fonte/dicionario.js); [transpilador.js](https://github.com/canarinho-js/canarinho/blob/HEAD/codigo_fonte/transpilador.js)
- In JavaScript regexes a word character is `[A-Za-z0-9_]` (plus case-folding exceptions with the `u` and `i` flags) and a word boundary sits between a word and a non-word character; accented letters are therefore non-word characters — [MDN: Word boundary assertion](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Regular_expressions/Word_boundary_assertion) (summarized; the page's own example `/\b\w+\b/.exec("café")` matches only "caf")
- Local probe (my own experiment, Node v24.21.0, consistent with the [MDN definition](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Regular_expressions/Word_boundary_assertion) above and with the [Canarinho](https://github.com/canarinho-js/canarinho/blob/HEAD/codigo_fonte/transpilador.js) code it imitates): a keyword that begins or ends with an accented letter cannot be anchored with `\b`; a Unicode-aware lookaround works; whole-source replacement also rewrites strings and comments; and NFC and NFD forms of the same keyword are different strings. Code and observed output:

```js
// helper modelled on Canarinho's traduzir(): one '\b' + key + '\b' regex, flag 'g', over the whole source
const traduzir = (codigo, dicionario) => Object.keys(dicionario).reduce(
  (acc, chave) => acc.replace(new RegExp('\\b' + chave + '\\b', 'g'), dicionario[chave]), codigo);

/\bé\b/.test('uai x é 5')                    // false  (also false with the u flag)
/\bocê\b/.test('ocê faz')                    // false  (ends in a non-ASCII letter)
/\bocê\b/.test('ocêx')                       // true   (only matches glued to an ASCII letter)
/\bfunção\b/.test('função x')                // true   (ends in an ASCII letter)
/\bno_máximo\b/.test('a no_máximo b')        // true
new RegExp('(?<![\\p{L}\\p{N}_])é(?![\\p{L}\\p{N}_])', 'u').test('uai x é 5')  // true
new RegExp('(?<![\\p{L}\\p{N}_])é(?![\\p{L}\\p{N}_])', 'u').test('café')       // false
traduzir('imprimir("se isso")', { se: 'if', imprimir: 'console.log' })  // 'console.log("if isso")'
traduzir('// se der erro',      { se: 'if' })                            // '// if der erro'
'ocê' === 'ocê'                   // false  (NFC 6f 63 ea versus NFD 6f 63 65 302)
new Function('var ocê = 1; var ocê = 2; return ocê !== ocê')()  // true: two distinct JS identifiers
```

- Hedy's first public evaluation counted 16.1% of errors as invalid characters, including accented letters and encoding problems — [ICER 2020 section 7.6](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf)
- Thengascript lists two keys for `var` that are different code-point sequences of the same word — [thengascript.js](https://github.com/makersofkerala/thengascript/blob/HEAD/thengascript.js)
- Python (PEP 3131): identifiers follow UAX #31, are converted to NFKC while parsing and compared by NFKC; the stdlib must stay ASCII-only; risks listed: round-tripping on screen/paper, confusable/mixed-script attacks, bidi display, weak tooling (summarized) — [PEP 3131](https://peps.python.org/pep-3131/)
- ECMAScript does the opposite: two IdentifierNames that are canonically equivalent "are not equal unless, after replacement of each UnicodeEscapeSequence, they are represented by the exact same sequence of code points"; identifiers follow UAX #31 with small modifications — [ECMAScript spec, Names and Keywords](https://tc39.es/ecma262/)
- Wenyan romanizes identifiers (pinyin, Baxter, unicode) on request — [types.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/types.ts)

**Reserved words versus user identifiers**
- Rockstar's grammar enumerates reserved words in a `keywords` Set; v2 added pronouns `you`, `i`, `me` and documents that this "will break programs which use `i` as an index variable" — [rockstar.peg](https://github.com/RockstarLang/satriani/blob/HEAD/satriani/rockstar.peg); [changes-from-v1](https://github.com/RockstarLang/rockstar/blob/HEAD/codewithrockstar.com/docs/11-changes-from-v1.md)
- Hedy free-text rules exclude keywords of both active languages through negative lookahead, and an overlap rule was proposed: a new language should not add keywords clashing with English ones unless the meaning is the same (summarized) — [level8.nl-Total.lark](https://github.com/hedyorg/hedy/blob/HEAD/grammars-Total/level8.nl-Total.lark); [discussion #776](https://github.com/hedyorg/hedy/discussions/776)
- Delégua reserves very short common Portuguese words (`e`, `de`, `em`, `como`, `cada`) — [palavras-reservadas.ts](https://github.com/DesignLiquido/delegua/blob/HEAD/fontes/lexador/palavras-reservadas.ts)
- Wenyan sidesteps collisions by quoting identifiers with 「」 — [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md)
- bhailangfun replaces `/sahi|galat|nalla/gi` with no boundaries and its author notes "have to improve this" — [interpreter.js](https://github.com/tuhinpal/bhailangfun/blob/HEAD/interpreter.js)
- Rockstar's own C# engine avoids .NET name collisions with a house rule (umlauts) — [design-decisions.md](https://github.com/RockstarLang/satriani/blob/HEAD/design-decisions.md)

**Mixing English API names and host interop**
- EsJS ships one plugin per JS built-in to map Spanish names to JS (`consola` to `console`; `escribir` to `log`), and generates its editor syntax and reserved-words table from the same keyword maps — [consola plugin](https://github.com/es-js/esjs/blob/HEAD/packages/core/src/plugins/consola/index.ts); [generate-esjs-syntax.js](https://github.com/es-js/esjs/blob/HEAD/packages/language-tools/src/generate-esjs-syntax.js)
- Canarinho maps `imprimir` to `console.log` and `info`, `erro`, `aviso` to `console.info`/`error`/`warn` in its dictionary; Delégua keeps a Delégua-to-JavaScript dictionary file for its JS translator and ships libraries "para Delégua e JavaScript" — [dicionario.js](https://github.com/canarinho-js/canarinho/blob/HEAD/codigo_fonte/dicionario.js); [dicionario-delegua-javascript.ts](https://github.com/DesignLiquido/delegua/tree/HEAD/fontes/tradutores/dicionarios); [org repos API](https://api.github.com/orgs/DesignLiquido/repos)
- Wenyan's stdlib is Wenyan with per-target folders; Hedy permits mixing only with English — [stdlib.ts](https://github.com/wenyan-lang/wenyan/blob/master/src/stdlib.ts); [discussion #776](https://github.com/hedyorg/hedy/discussions/776) (summarized)
- Multilingual precedents: ALGOL 68 supported several natural languages; Rapture mixes Russian and English keywords in one file; BabylScript mixes 12 languages across statements but not inside one — [SPLASH-E 2023 section 3.11](https://doi.org/10.1145/3622780.3623645)

**Error messages: quality and localization**
- Evidence on need: Guo's CHI 2018 survey (840 responses, 86 countries, 74 native languages) found barriers in reading instructional material, technical communication, reading and writing code, and learning English and programming simultaneously; respondents wanted "simplified English without culturally-specific slang" in instructional materials — [Guo, CHI 2018](https://doi.org/10.1145/3173574.3173970); [abstract text](https://pg.ucsd.edu/publications/non-native-english-speakers-learning-programming_CHI-2018.txt)
- Becker (PPIG 2019): few studies exist on human language in learning programming; error messages already trouble novices and the difficulty is "likely compounded" for non-native English speakers — [Becker, PPIG 2019](https://ppig.org/files/2019-PPIG-30th-becker.pdf)
- Error messages "can be localized with relative ease, compared to keywords or productions" but professional languages rarely do it; Hedy and Scratch do — [SPLASH-E 2023 section 3.12](https://doi.org/10.1145/3622780.3623645)
- Hedy implements localization via gettext keys, Weblate and Flask-Babel — [error-messages.txt](https://github.com/hedyorg/hedy/blob/HEAD/content/error-messages.txt); [README](https://github.com/hedyorg/hedy#readme)
- Elm's 2015 write-up (Elm 0.15.1) of "Compiler Errors for Humans": locate the code by showing it "exactly as you wrote it" with line numbers; give every message a hint with specific context; use colour in two ways (red draws attention to the problem, blue separates messages); put general context above the code and specifics below; "nobody wants a confusing and rude gatekeeper"; a `--report=json` flag feeds editor plugins — [Elm: Compiler Errors for Humans](https://elm-lang.org/news/compiler-errors-for-humans); [source](https://github.com/elm/elm-lang.org/blob/HEAD/pages/news/compiler-errors-for-humans.elm)
- Marceau, Fisler and Krishnamurthi studied beginning students' interactions with the vocabulary and source highlighting of DrRacket's messages; main finding: the messages "significantly fail to convey information accurately to students" (summarized) — [Onward! 2011](https://cs.brown.edu/~sk/Publications/Papers/Published/mfk-mind-lang-novice-inter-error-msg/); an earlier study found "many novices still struggle to work effectively with DrScheme's error messages" — [SFP 2010 abstract](https://cs.brown.edu/~sk/Publications/Papers/Published/mfk-measur-effect-error-msg-novice/)
- In Hedy's child study, children often did not fully understand error messages and skipped punctuation when reading them aloud — [Gilsing, Pelay, Hermans 2022](https://doi.org/10.1016/j.cola.2022.101158)

**Humor in diagnostics (examples)**
- ArnoldC's default parse error constant is "WHAT THE FUCK DID I DO WRONG" — [ArnoldParser.scala](https://github.com/lhartikk/ArnoldC/blob/HEAD/src/main/scala/org/arnoldc/ArnoldParser.scala)
- Bhai-lang errors stay in persona and quote the offending keyword: `Variable "${identifier}" bana to le pehle.` and `Kya "bas kar bhai"?? Loop kahan hai?`; its null-error class is `NallaPointerException` (evidently a pun on NullPointerException) — [interpreter components](https://github.com/DulLabs/bhai-lang/tree/HEAD/packages/interpreter/src/components); [nallaPointerException.ts](https://github.com/DulLabs/bhai-lang/blob/HEAD/packages/parser/src/exceptions/nallaPointerException.ts)
- BIRL and Rockstar READMEs use the same joking voice outside the compiler (taglines, a "But why?" section) — [BIRL README](https://github.com/birl-language/birl-language.github.io); [Satriani README](https://github.com/RockstarLang/satriani)

### Inferences
- Multi-word keywords are easiest when each is a single lexeme (GoiásScript's underscore forms such as `se_num_for` already are, per its project guide); a longest-match table is only needed if multi-word forms contain spaces.
- Normalization is the most important accent decision for a JS-targeting dialect: ECMAScript treats canonically equivalent identifiers as different, Python normalizes (NFKC), and the probe shows an NFC keyword table does not match NFD input. Normalizing source and keyword table to one form (NFC) at lexer entry, registering accented and unaccented keyword spellings to the same token (Delégua), and deciding whether identifiers are diacritic sensitive are separate, explicit decisions.
- GoiásScript's documented keywords include accented forms at word edges (`é`, `ocê`, `é_igualim`; also `se_não`, `no_máximo`, `pelo_menos`) per its [project guide](<repo>/CLAUDE.md). If any component anchors keywords with `\b`, `é` and `ocê` cannot match (probe); a Unicode-aware lookaround or a real tokenizer avoids this. I did not inspect GoiásScript's implementation.
- Keep reserved words rare and specific; short common words (Delégua's `e`, `de`) cost users good identifiers. Contextual keywords or guards (Hedy lookaheads, Rockstar keyword set) are alternatives to delimiters.
- Treat English host API names as an explicit alias layer (EsJS) generated from one table that also feeds docs and highlighters.
- Humor is common in joke languages but I found no empirical evidence about its effect; the evidence available (Guo on slang, Marceau on vocabulary, Hedy on children misreading messages) argues for a plain-Portuguese core message (what, where, how to fix, with the code shown as written) and dialect flavor as a separable layer, e.g. a prefix or suffix, so it can be switched off.
- Guo's finding concerns culture-specific English slang for non-native speakers; by analogy, Goiás-specific slang could be a comprehension barrier for Brazilians from other regions. This is my inference; no study of regional-Portuguese programming vocabulary was found.
- Put message text in a catalog from day one (gettext-style keys) even for a single language; it also allows a neutral-Portuguese mode.

### Gaps
- No study of humor in compiler diagnostics was found (search returned only related work on clarity).
- Hedy discussion #776 (as summarized) does not discuss diacritics; no source describes how Delégua or Égua normalize Unicode input.
- Guo's full paper was not read (abstract only); I could not verify what it says about localized keywords specifically.
- The probe covers Node v24 only and only the characters `é` and `ê`; other Portuguese characters (`ç`, `ã`, `õ`) were not tested individually, though they are likewise non-word characters under the MDN definition.

## 6. Tooling sets that drove adoption: playground, VS Code, tree-sitter, formatter, REPL, package manager, minimal viable set

### Takeaway
Projects that spread shipped a zero-install browser playground, an npm/CLI entry point, cheap editor highlighting generated from the keyword table, and runnable docs; LSP, tree-sitter, formatters and package managers appear mostly in better-resourced or older ecosystems (Delégua, Hedy) or as third-party contributions (Wenyan).

### Cited Findings
**Official platform facts**
- VS Code TextMate grammars are "a structured collection of regular expressions" (Oniguruma), declared under `contributes.grammars`, with scopes such as `keyword.operator.arithmetic.js`; only JSON grammars load directly; semantic highlighting "is considered an addition to the TextMate-based syntax highlighting" (summarized) — [VS Code syntax highlight guide](https://code.visualstudio.com/api/language-extensions/syntax-highlight-guide)
- Semantic tokens come from a `DocumentSemanticTokensProvider` (usually backed by a language server) layered over the TextMate result, and themes must opt in (summarized) — [VS Code semantic highlight guide](https://code.visualstudio.com/api/language-extensions/semantic-highlight-guide)
- A language server is a separate process with a client extension and a server; it exists because language features can be resource intensive and to avoid M x N editor integrations; the guide states "an error tolerant parser is necessary for a Language Server" (summarized) — [VS Code language server guide](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide)
- Tree-sitter is "a parser generator tool and an incremental parsing library" aiming to be general, fast enough to parse on every keystroke, robust to syntax errors, and dependency-free (pure C11) (summarized) — [Tree-sitter docs](https://tree-sitter.github.io/tree-sitter/)

**What the projects shipped**
- Wenyan: online IDE, `@wenyan/core` and CLI, wyg package manager, highlighters (CodeMirror/Prism/TextMate) generated from the compiler's keyword table, SVG renderer; VS Code, Vim and Sublime plugins and a decompiler were third-party — [README](https://github.com/wenyan-lang/wenyan/blob/master/README.md); [highlight keywords.js](https://github.com/wenyan-lang/highlight/blob/HEAD/scripts/keywords.js)
- Hedy: browser-based, no install, phone and tablet friendly; Lezer highlighting grammars per level; Weblate for translations — [ICER 2020](https://hedy.org/research/Hedy_A_Gradual_Language_for_Programming_Education_2020.pdf); [highlighting/](https://github.com/hedyorg/hedy/tree/HEAD/highlighting); [README](https://github.com/hedyorg/hedy#readme)
- Rockstar: WASM interpreter embedded in the site, native binaries, CodeMirror language package, docs examples shared with the test suite — [Rockstar README](https://github.com/RockstarLang/rockstar); [rockstar2 README](https://github.com/RockstarLang/rockstar2)
- Égua: web IDEgua with keyword autocomplete, npm CLI with REPL, VitePress docs — [Égua README](https://github.com/eguadev/egua)
- Delégua: VS Code extension (172 stars) and debugger, web editor, `<script>` runner, formatter (`estilizador` with rule files), translators including reverse translators — [Delégua README](https://github.com/DesignLiquido/delegua); [org repos API](https://api.github.com/orgs/DesignLiquido/repos); [tree API](https://api.github.com/repos/DesignLiquido/delegua/git/trees/HEAD?recursive=1)
- EsJS: playground app, CLI, VS Code extension, Vite plugin, and `language-tools` generating a TextMate grammar (stock JavaScript grammar plus Spanish keyword patterns), snippets, language configuration and a reserved-words table from the keyword maps — [EsJS README](https://github.com/es-js/esjs); [generate-esjs-syntax.js](https://github.com/es-js/esjs/blob/HEAD/packages/language-tools/src/generate-esjs-syntax.js)
- Bhai-lang: docs site with a playground, npm CLI; UrduScript: CodeMirror web editor and CLI; Canarinho: npm CLI with reverse translation (`-i`) and recursive (`-r`) modes — [bhai-lang README](https://github.com/DulLabs/bhai-lang); [UrduScript](https://github.com/asadm/urduscript); [Canarinho README](https://github.com/canarinho-js/canarinho)
- Reverse translators (target language back to the dialect) exist in Canarinho (`-i`), Delégua (reverse translators from JavaScript and Python) and Wenyan ("wenyanizer", third-party) — [Canarinho README](https://github.com/canarinho-js/canarinho); [tradutores/](https://github.com/DesignLiquido/delegua/tree/HEAD/fontes/tradutores); [Wenyan README](https://github.com/wenyan-lang/wenyan/blob/master/README.md)
- Legesher built a Tree-sitter Python grammar for its localized Python (46 stars) — [tree-sitter-legesher-python](https://github.com/legesher/tree-sitter-legesher-python)
- Portugol Studio keeps two lexers: ANTLR for the language and a `.flex` file for the editor — [repo tree](https://api.github.com/repos/UNIVALI-LITE/Portugol-Studio/git/trees/HEAD?recursive=1)
- Package manager traction is small where measurable: Wenyan's `wyg` has 43 stars versus 20,284 for the language — [org repos API](https://api.github.com/orgs/wenyan-lang/repos)
- Elm's machine-readable error output (`--report=json`) was introduced to enable editor integration — [Elm blog](https://elm-lang.org/news/compiler-errors-for-humans)

### Inferences
- Minimal viable set suggested by the evidence: (1) zero-install web playground, (2) npm CLI (with REPL optional), (3) TextMate or CodeMirror grammar generated from the keyword table (Wenyan, EsJS), (4) docs with runnable examples that also run as tests (Rockstar), (5) structured (JSON) error output to leave a door open for editors, (6) optionally a reverse translator (JS to dialect) as an onboarding aid.
- A language server needs an error-tolerant parser (per VS Code's guide) and a second process; for a regex- or macro-based transpiler this is a large step, so LSP, tree-sitter, formatter and package manager are later-stage items.
- Duplicated lexers (Portugol Studio's ANTLR plus `.flex`) show the drift risk that generating highlighters from one keyword table (Wenyan `highlight`, EsJS `language-tools`) avoids.
- Third-party plugins (Wenyan) appear after the language is popular; they are not a prerequisite.

### Gaps
- Monaco's Monarch tokenizer and CodeMirror 6 language-package guidance were not researched; Tree-sitter grammar authoring (grammar DSL) was not covered by the page fetched.
- No data links any single tool to adoption causally; VS Code extension install counts were not retrieved.
- Lezer is assumed to be CodeMirror 6's parsing system (general knowledge, not verified here).

## 7. Scope control for a solo maintainer; versioning and specs for small languages

### Takeaway
Long-lived small languages either freeze a small normative spec and grow conformance tests (LOLCODE), keep old fixtures and document breaking changes (Rockstar 2), or tie versions to a pedagogical roadmap with institutional support (Hedy); solo-maintained projects (EsJS, Rockstar, Wenyan's two maintainers) show high key-person risk, rewrites and dormancy.

### Cited Findings
- LOLCODE's spec deliberately ships "incomplete" because adding is easier than changing; it was published as dated drafts (1.2 on 2007-07-12) with a later 1.3, and `lci` tracks spec versions by tag — [spec 1.2](https://github.com/justinmeza/lolcode-spec/blob/HEAD/v1.2/lolcode-spec-v1.2.md); [lci README](https://github.com/justinmeza/lci)
- Rockstar: a 2024 rewrite from JS to C#/.NET, v1 fixtures retained (87 files) with a compatibility shim for v1 poetic literals, a "changes from Rockstar 1" document, and the old engine archived; the top contributor has 394 commits among 56 contributors — [changes-from-v1](https://github.com/RockstarLang/rockstar/blob/HEAD/codewithrockstar.com/docs/11-changes-from-v1.md); [tree API](https://api.github.com/repos/RockstarLang/rockstar/git/trees/HEAD?recursive=1); [contributors API](https://api.github.com/repos/RockstarLang/rockstar/contributors)
- Wenyan: semver-style npm releases with documented breaking change in v0.3.0, a wiki warning that the API changes often, last release commit 2021-06-09, last master commit 2023-01-17, 217 open issues; the creator said survival depended on a user community — [CHANGELOG](https://github.com/wenyan-lang/wenyan/blob/master/CHANGELOG.md); [wiki](https://github.com/wenyan-lang/wenyan/wiki/Compiler-API); [commits API](https://api.github.com/repos/wenyan-lang/wenyan/commits); [IEEE Spectrum](https://spectrum.ieee.org/classical-chinese)
- Hedy: scope is defined as "teach Python" (levels end at a subset of Python); #776 split localization into staged tasks and limited mixing to English plus one language; the formalism paper treats levels (vertical) and locales (horizontal) as orthogonal axes; formal-semantics experiments and research papers live in the repo; Weblate carries translation work — [README](https://github.com/hedyorg/hedy#readme); [discussion #776](https://github.com/hedyorg/hedy/discussions/776) (summarized); [Gradual Grammars](https://homepages.cwi.nl/~storm/publications/gradual-grammars.pdf)
- Delégua keeps the core limited by moving processor-architecture and WebAssembly backends to separate packages that depend on the core only for lexer, parser and AST types; the project is a fork of Égua 1.2.0 with only partial compatibility — [Delégua README](https://github.com/DesignLiquido/delegua)
- Concentration of commits: EsJS 645 by one of 4 contributors; Potigol 186 by the main author; Portugol Studio 140 by the main author of 9; ArnoldC is a small repo (top contributor 24 commits, 11 contributors) — [EsJS contributors](https://api.github.com/repos/es-js/esjs/contributors); [Potigol contributors](https://api.github.com/repos/potigol/potigol/contributors); [Portugol Studio contributors](https://api.github.com/repos/UNIVALI-LITE/Portugol-Studio/contributors); [ArnoldC contributors](https://api.github.com/repos/lhartikk/ArnoldC/contributors)
- Last-push dates after virality: BIRL's website repo (940 stars) 2018-09-02; ArnoldC (6,888 stars) 2024-01-31; Bhai-lang (4,094 stars) 2024-06-15; UrduScript 2023-07-11 — [BIRL org](https://api.github.com/orgs/birl-language/repos); [ArnoldC repo](https://github.com/lhartikk/ArnoldC); [Bhai-lang API](https://api.github.com/repos/DulLabs/bhai-lang); [UrduScript](https://github.com/asadm/urduscript)
- Legesher is mid-rewrite with the old code pinned as legacy — [legesher/legesher](https://github.com/legesher/legesher)

### Inferences
- Pin a small normative core now (keyword table, grammar, semantics notes) and add by extension, in the spirit of LOLCODE's baseline rule; keep a dated "changes from vX" page when something breaks (Rockstar).
- Keep heavy backends, dialect variants and ecosystems outside the core (Delégua), and avoid starting sibling languages (HTML/CSS/Vue variants) before the compiler is stable.
- Separate "language version" from "compiler/API version" (Wenyan's breaking `compile` change vs. the language) and make conformance fixtures the contract between them.
- Single-source keyword and message tables are the main maintainability lever for a one-person project.
- Key-person risk is the norm among comparable projects; documentation, tests and small surface area are the mitigation. A stale last-push date is only a proxy: a finished, stable project can look dormant.

### Gaps
- No source on how much time maintainers spend or how they decided what to exclude; the above is from repository evidence only.
- No authoritative guidance on versioning small languages was found beyond these examples.

## 8. Cross-cutting: adoption, virality, education, and failure signals

### Takeaway
Novelty languages spike on launch (HN, Twitter) and then depend on one maintainer; education-focused languages grow through teachers, translators and institutions and are nearly invisible on HN. GitHub stars are a poor proxy for real usage.

### Inferences
- Virality recipe seen repeatedly: a one-sentence concept, a runnable demo with zero install, a spec or README that invites implementations, and a shareable artifact (stickers, SVG pages, quotable keywords). Humor-first languages (Rockstar, ArnoldC, BIRL, Bhai-lang) peak at launch; education-first languages (Hedy, Portugol, Delégua) show steadier activity.
- Failure pattern: viral launch, then one maintainer, no spec/tests contract, no education channel, then dormancy (BIRL, ArnoldC, Bhai-lang, Wenyan since 2023).
- For GoiásScript (playful but serious), the combination that none of the humor-first projects built is a conformance suite plus teaching material; the education-first Brazilian projects lack the playful regional identity.

### Gaps
- No traffic, npm-download or install-count data were gathered; stars and HN points are weak proxies.
- Causal claims about what drove adoption are inferences from timelines, not measured.
