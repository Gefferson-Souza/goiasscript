## 1. Hand-written lexer design for goianês keywords

### Takeaway
Every production JS scanner I inspected (TypeScript, esbuild, oxc, V8, acorn, meriyah) is hand-written and maximal-munch, and each resolves the regex/division, template-`}` and ASI ambiguities from context rather than with a pure regular grammar. Because `_` is an ECMAScript ID_Continue character, every underscore-joined goianês keyword is lexically an ordinary identifier that a maximal-munch scan reads whole and then looks up; JavaScript never normalizes identifiers, so the NFC-versus-NFD policy for `é`, `ocê`, `se_não` is a decision the new compiler must make explicitly (UAX #31 points to NFC for case-sensitive languages; Rust uses NFC, Python NFKC).

### Cited Findings

#### Maximal munch and lexical goal symbols
- ECMAScript source text is "scanned from left to right, repeatedly taking the longest possible sequence of code points as the next input element"; there are five lexical goal symbols because token identification "is sensitive to the syntactic grammar context": `InputElementHashbangOrRegExp` (start of a Script/Module), `InputElementRegExpOrTemplateTail`, `InputElementRegExp`, `InputElementTemplateTail`, and `InputElementDiv` in all other contexts — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- Source text is a sequence of Unicode code points and "the actual encodings used to store and interchange ECMAScript source text is not relevant to this specification" — [ECMA-262, Source Text](https://tc39.es/ecma262/multipage/ecmascript-language-source-code.html)
- Maximal munch: "whichever one matches the most characters wins"; consequence: "we can't easily detect a reserved word until we've reached the end of what might instead be an identifier" — [Crafting Interpreters, Scanning](https://craftinginterpreters.com/scanning.html)

#### Identifier syntax, keywords and reserved words (spec)
- `IdentifierStartChar` is `UnicodeIDStart`, `$` or `_`; `IdentifierPartChar` is `UnicodeIDContinue` or `$`; "The nonterminal IdentifierPart derives _ via UnicodeIDContinue"; the ID_Start/ID_Continue sets include Other_ID_Start/Other_ID_Continue — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- Identifiers may contain `\u` escapes but keywords may not: "A code point in a keyword cannot be expressed by a \ UnicodeEscapeSequence" — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- "Two IdentifierNames that are canonically equivalent according to the Unicode Standard are not equal unless, after replacement of each UnicodeEscapeSequence, they are represented by the exact same sequence of code points", i.e. JavaScript does no identifier normalization — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- "A reserved word is an IdentifierName that cannot be used as an identifier"; the `ReservedWord` list contains `in` but not `of` or `async`; `await`/`yield` are contextual; `let`, `static`, `implements`, `interface`, `package`, `private`, `protected`, `public` are disallowed only in strict mode; "async is not reserved" — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- [local] JS compares identifiers by exact code points: `'é'` (U+00E9) and `'é'` are not `===` (UTF-16 lengths 1 and 2); acorn 8.19.0 accepts `let é = 1; let é = 2;` as two distinct bindings and rejects a duplicate in the same form; U+0301 is ID_Continue but not ID_Start, and `/^\p{ID_Start}\p{ID_Continue}*$/u` matches the decomposed form — [verify.mjs](file://<scratchpad>/bench-scripts/verify.mjs), [acorn 8.19.0](https://cdn.jsdelivr.net/npm/acorn@8/dist/acorn.min.js)
- [local] Reserved words are legal property names in JS (acorn accepts `obj.const = 1; ({ const: 2, class() {} });` and `var o = { if: 1 }; o.if;`) — [verify.mjs](file://<scratchpad>/bench-scripts/verify.mjs), [acorn 8.19.0](https://cdn.jsdelivr.net/npm/acorn@8/dist/acorn.min.js)
- Oxc's Rust AST keeps distinct node types `BindingIdentifier`, `IdentifierReference` and `IdentifierName` instead of ESTree's single `Identifier` — [Oxc parser architecture](https://oxc.rs/docs/learn/architecture/parser.html)

#### Unicode: UAX #31, UAX #15, UCD, precedents
- UAX #31 (Unicode 18.0.0, revision 45, dated 2026-09-01): "UAX31-R4. Equivalent Normalized Identifiers: ... an implementation shall specify the Normalization Form ... any two identifiers that have the same Normalization Form shall be treated as equivalent" — [UAX #31](https://unicode.org/reports/tr31/)
- UAX #31: "Generally if the programming language has case-sensitive identifiers, then Normalization Form C is appropriate; whereas, if the programming language has case-insensitive identifiers, then Normalization Form KC is more appropriate"; a profile that relies on identifier closure under normalization "should conform to UAX31-R4 using NFC, not NFKC" — [UAX #31](https://unicode.org/reports/tr31/)
- UAX #31 defines ID_Continue as ID_Start plus General_Category Mn, Mc, Nd, Pc plus Other_ID_Continue, minus Pattern_Syntax and Pattern_White_Space; "unless the property is designed to be stable (such as XID_Continue), code points could be removed in a future version of Unicode"; default identifiers remain "subject to spoofing issues arising from invisible characters, visually identical characters, or bidirectional reordering", for which UTS #39 mechanisms are recommended — [UAX #31](https://unicode.org/reports/tr31/)
- UAX #31 uses NFD only inside its case-insensitive match definition ("canonical decomposition (NFD) followed by the toNFKC_Casefold operation"), not as a recommended identity form — [UAX #31](https://unicode.org/reports/tr31/)
- UAX #15: NFC "uses canonical composite characters where possible"; "Typical strings of composite accented Unicode characters are already in Normalization Form C"; W3C specifications "recommend using Normalization Form C for all content" — [UAX #15](https://unicode.org/reports/tr15/)
- UnicodeData: é U+00E9 decomposes to 0065 0301, ê U+00EA to 0065 0302, ã U+00E3 to 0061 0303, õ U+00F5 to 006F 0303, ç U+00E7 to 0063 0327; U+0301/0302/0303/0327 are General_Category Mn — [UnicodeData.txt](https://www.unicode.org/Public/UCD/latest/ucd/UnicodeData.txt)
- Rust: "Identifiers are normalized using Normalization Form C (NFC) ... Two identifiers are equal if their NFC forms are equal" — [Rust Reference, Identifiers](https://doc.rust-lang.org/reference/identifiers.html)
- Python: "All names are converted into the normalization form NFKC while parsing" — [Python Language Reference, Lexical analysis](https://docs.python.org/3/reference/lexical_analysis.html)
- Trojan Source (CVE-2021-42574, homoglyph variant CVE-2021-42694): compilers and build pipelines should warn or fail on unterminated bidirectional control characters in comments and string literals and on identifiers that mix scripts confusably — [trojansource.codes](https://trojansource.codes/)
- [local] Node v24.21.0 reports `process.versions.unicode` = 17.0 (ICU 78.3), one Unicode version behind UAX #31 revision 45 (Unicode 18.0.0) — [verify.mjs](file://<scratchpad>/bench-scripts/verify.mjs), [UAX #31](https://unicode.org/reports/tr31/)
- Delegua (Portuguese-keyword language in TypeScript, 490 GitHub stars, last push 2026-10-06) lists accented and unaccented spellings as separate keyword-table entries (`assercao`/`asserção`, `contem`/`contém`) plus an English alias (`const`) — [Delegua reserved words](https://raw.githubusercontent.com/DesignLiquido/delegua/principal/fontes/lexador/palavras-reservadas.ts), [repo metadata](https://api.github.com/repos/DesignLiquido/delegua)
- Delegua has one lexer class per dialect (`lexador-egua-classico`, `-guarani`, `-pitugues`, `-portugol-ipt`, `-prisma`, `-tenda`, `-calango`) — [Delegua lexer dialects](https://api.github.com/repos/DesignLiquido/delegua/contents/fontes/lexador/dialetos)

#### Keyword recognition and Unicode tables in production scanners
- V8 scans UTF-16; ASCII identifier characters are classified by a 128-entry flag table; keywords are lowercase-only so non-keyword identifiers exit early; keyword lookup is a gperf perfect hash on length plus first two characters, followed by a compare only if lengths match — [V8, Blazingly fast parsing part 1](https://v8.dev/blog/scanner)
- V8: ID_Start/ID_Continue property lookups "are expensive, so V8 caches them"; surrogate pairs are combined only when an unrecognized character starts a token or in the non-ASCII identifier slow path; reported [vendor] speedups from the scanner work: about 1.4x single tokens, 1.3x strings, 2.1x multiline comments, 1.2x to 1.5x identifiers — [V8, Blazingly fast parsing part 1](https://v8.dev/blog/scanner)
- V8 benchmarking caution: sites that look faster in MB/s "often have lower information density and produce fewer tokens per second" — [V8, Blazingly fast parsing part 1](https://v8.dev/blog/scanner)
- TypeScript `getIdentifierToken`: "Reserved words are between 2 and 12 characters long and start with a lowercase letter", then a `Map` lookup (`textToKeyword`); ID_Start/ID_Continue come from static range tables (`unicodeESNextIdentifierStart`/`Part`) — [TypeScript 5.9 scanner.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/scanner.ts)
- esbuild's keyword table is a Go `map[string]T` — [esbuild js_lexer.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_lexer/js_lexer.go); acorn builds a per-version keyword regexp (`wordsRegexp`) and generated non-ASCII/astral identifier tables — [acorn state.js](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/src/state.js), [acorn identifier.js](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/src/identifier.js)
- Meriyah splits its lexer by token class: `src/lexer/` has `scan.ts` (20 KB), `charClassifier.ts` (11 KB), `numeric.ts` (9 KB), `identifier.ts` (9 KB), `string.ts` (8 KB), `comments.ts` (5 KB), `regexp.ts` (5 KB), `template.ts` (4 KB) — [Meriyah tree (GitHub API)](https://api.github.com/repos/meriyah/meriyah/git/trees/main?recursive=1)

#### Regex vs division, template literals, ASI and numeric separators
- esbuild: "The parser is separate from the lexer"; "The lexer is called on the fly as the file is parsed instead of lexing the entire input ahead of time" because "which token is parsed depends on the semantic context" (regex vs division, JSX vs less-than); lookahead "kept to one token in almost all cases", the TypeScript exception being `trySkipTypeScript*WithBacktracking()` — [esbuild architecture.md](https://raw.githubusercontent.com/evanw/esbuild/main/docs/architecture.md)
- esbuild's `parsePrefix` calls `p.lexer.ScanRegExp()` when `/` or `/=` appears where an expression must start, and `RescanCloseBraceAsTemplateToken()` turns a `}` back into a template continuation — [esbuild js_parser.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_parser/js_parser.go), [esbuild js_lexer.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_lexer/js_lexer.go)
- TypeScript's scanner exposes parser-driven re-scans: `reScanSlashToken`, `reScanTemplateToken`, `reScanTemplateHeadOrNoSubstitutionTemplate`, `reScanGreaterToken`, `reScanLessThanToken`, `reScanQuestionToken`, `reScanHashToken`, `reScanAsteriskEqualsToken`, `reScanJsxToken`; the regex re-scan documents Unicode Sets mode and nested character class rules — [TypeScript 5.9 scanner.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/scanner.ts); the Go port keeps `ReScanSlashToken` and `ReScanTemplateToken` — [typescript-go scanner.go](https://raw.githubusercontent.com/microsoft/typescript-go/main/internal/scanner/scanner.go)
- Oxc's parser cursor has `re_lex_template_substitution_tail`, `re_lex_right_angle`, `re_lex_ts_l_angle`, `re_lex_ts_r_angle` plus `checkpoint`/`rewind`/`lookahead`; its docs call the lexer "context-aware" for regex vs division and say it uses SIMD for whitespace skipping — [Oxc cursor.rs](https://raw.githubusercontent.com/oxc-project/oxc/main/crates/oxc_parser/src/cursor.rs), [Oxc parser architecture](https://oxc.rs/docs/learn/architecture/parser.html)
- acorn keeps a tokenizer-side context stack (`b_stat`, `b_expr`, `b_tmpl` for `${`, `q_tmpl` for the backtick with `tryReadTemplateToken`, `p_stat`, `f_expr`, ...), an `exprAllowed` flag, and a `braceIsBlock(prevType)` function with about ten cases (colon, `return`, `else`, `;`, EOF, `)`, `=>`, `{`, `var`/`const`/name, line-break test after `return`/name) — [acorn tokencontext.js](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/src/tokencontext.js)
- Generator-based JS grammars still need hand-written lexical code: tree-sitter-javascript declares `externals` for `_automatic_semicolon`, `_template_chars`, `_ternary_qmark` (its C scanner also has HTML-comment and logical-or tokens) — [tree-sitter-javascript grammar.js](https://raw.githubusercontent.com/tree-sitter/tree-sitter-javascript/master/grammar.js), [scanner.c](https://raw.githubusercontent.com/tree-sitter/tree-sitter-javascript/master/src/scanner.c); the ANTLR JavaScript grammar ships hand-written base classes: the lexer base decides regex vs division from the previous token (`IsRegexPossible()`: after certain tokens "no regex literal can follow", "in all other cases, a regex literal _is_ possible"), tracks template-string braces (`ProcessTemplateOpenBrace`/`ProcessTemplateCloseBrace`, `IsInTemplateString`) and strict-mode scopes (`ProcessOpenBrace`/`ProcessCloseBrace`), and the parser base provides `notLineTerminator()`, `lineTerminatorAhead()`, `closeBrace()`, `notOpenBraceAndNotFunction()`; the grammar directory has per-target subdirectories (CSharp, Cpp, Go, Java, JavaScript, Python3) beside the `.g4` files — [JavaScriptLexerBase.java](https://raw.githubusercontent.com/antlr/grammars-v4/master/javascript/javascript/Java/JavaScriptLexerBase.java), [JavaScriptParserBase.java](https://raw.githubusercontent.com/antlr/grammars-v4/master/javascript/javascript/Java/JavaScriptParserBase.java), [directory listing](https://api.github.com/repos/antlr/grammars-v4/contents/javascript/javascript)
- ASI has three rules (offending token preceded by a LineTerminator, or `}`, or the `)` ending a do-while; end of input; restricted productions) with the override that "a semicolon is never inserted automatically if the semicolon would then be parsed as an empty statement or ... one of the two semicolons in the header of a for statement" — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- Restricted productions in the live spec (fetched 2026-10-13): postfix `++`/`--`, `continue`/`break`/`return`/`throw`/`yield`, arrow `=>`, `async`, and the newer `using` declaration; "if a MultiLineComment contains a line terminator code point, then the entire comment is considered to be a LineTerminator for purposes of parsing by the syntactic grammar" — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- Implementations record a per-token newline flag: TypeScript `canParseSemicolon()` accepts `;`, `}`, EOF or `scanner.hasPrecedingLineBreak()`, and arrow detection after `async` returns false if a line break precedes — [TypeScript 5.9 parser.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/parser.ts); esbuild `HasNewlineBefore` — [esbuild js_lexer.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_lexer/js_lexer.go); V8 "tracks newlines while skipping whitespace" — [V8 blog](https://v8.dev/blog/scanner)
- Numeric separators: the grammar defines `NumericLiteralSeparator :: _` with a `[+Sep]` parameter on the decimal and non-decimal literal productions — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html); TypeScript's `scanNumberFragment` reports 6188 "Numeric separators are not allowed here." and 6189 "Multiple consecutive numeric separators are not permitted." — [TypeScript scanner.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/scanner.ts), [diagnosticMessages.json](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/diagnosticMessages.json)

### Inferences
- Maximal munch plus `_` in ID_Continue means `se_ocê_quiser`, `se_num_for`, `vai_na_frente_faz_trem`, `é_igualim` and `maior_que` are each one identifier-shaped token; prefix overlaps such as `se` / `se_não` / `se_num_for` never need a trie or longest-match logic beyond reading the whole `ID_Start ID_Continue*` run and then doing one table lookup. `[no LineTerminator here]` restrictions inside a JS two-token construct (e.g. `async function`) disappear automatically when a single goianês token spells it.
- The keyword table should be plain data (`Map<string, TokenKind>`), not code: TypeScript and esbuild use map lookups; V8's gperf is a throughput optimization the project does not need for programs of a few KB. Do not copy TypeScript's "2 to 12 characters" prefilter, since goianês keywords reach 22 characters (`vai_na_frente_faz_trem`). Keep an ASCII fast path and a Unicode slow path as V8 does.
- Classify every goianês word with the same categories the spec uses (always reserved, strict-mode reserved, contextual keyword, plain identifier). `em` (in) must be reserved because `in` is; `de` (of) can be contextual because `of` is not a ReservedWord. Goianês keywords are everyday words (`trem`, `uai`, `de`, `em`, `mais`, `nada`), so the collision risk with user identifiers is much higher than in English-keyword JS; keep the reserved set minimal and accept reserved words as property names exactly as JS does ([local] result above), which means "keyword or IdentifierName?" is decided by parser position, not by the lexer alone.
- Normalization policy that follows from the sources: normalize identifier-like tokens (not the whole file) to NFC before the keyword lookup and before interning, keep keyword spellings stored in NFC, and keep all spans in original-source coordinates. Whole-file normalization would change string-literal and comment contents (a runtime-visible change, since JS strings are code-unit sequences) and shift offsets used by diagnostics and source maps. NFC is what UAX #31 names for case-sensitive languages and what Rust does; NFKC (Python) is unnecessary for Latin letters plus accents; NFD has no standing as an identity form. Without any normalization a decomposed `é` typed or pasted into a keyword would lex as a plain identifier (U+0301 is ID_Continue) and fail later with a confusing message, so either normalize or diagnose.
- Accent-insensitive aliases (`senao`, `se_nao`, `se_não`) are safest as explicit table entries (the Delegua approach, and the project's own CLAUDE.md lists both `senao` and `se_não`). Diacritic folding via NFD would make a user variable `oce` silently mean `ocê` (`this`).
- Because the language allows non-ASCII identifiers, the lexer is the cheap place for Trojan Source checks (bidi controls in comments and strings, mixed-script confusables) and for pinning the Unicode tables: a runtime `\p{ID_Start}` check inherits the host's Unicode version (Node 24 is on 17.0 while UAX #31 is at 18.0), so compiler output could differ across Node/browser versions; generated static tables (the TypeScript/acorn approach) make results deterministic.
- For regex-vs-division and template `}`, the parser-driven re-scan used by TypeScript, esbuild and oxc is exact; the acorn-style tokenizer context stack needs the long `braceIsBlock` heuristic and is the older design. A standalone token stream for syntax highlighting can still use a previous-token heuristic and accept imprecision. Keep template text, string literals, comments and regex bodies as separate token kinds so goianês keywords are never substituted inside them (the failure mode of the current regex-substitution transpiler).
- Scope cut available: regex literal bodies could be scanned to the closing `/` plus flags without validating the pattern (TypeScript's re-scan shows what full validation involves), leaving invalid patterns to the JS engine.
- Because `_` is both the numeric separator and the word joiner, there is no lexical conflict (numbers start with a digit), but the lexer should produce TypeScript-style targeted diagnostics for separator misuse, and a dedicated hint for pt-BR habits such as `1.000,50` (idea, not sourced).
- Dated practices: regex substitution over source text (ignores strings, comments, templates, regexes, property names); tokenizing the whole file before parsing (esbuild explicitly lexes on demand because of regex and JSX); tokenizer-side context stacks for regex detection.

### Gaps
- No published comparison of keyword-lookup strategies (perfect hash vs Map vs switch vs trie) in a JS/TS lexer; only V8's native-code numbers and the code of TypeScript/esbuild/acorn were found.
- I did not find a standard or best-practice document specifically about NFC vs NFD for non-English keywords; the NFC recommendation is derived from UAX #31, UAX #15 and the Rust precedent. I did not check whether Delegua's lexer normalizes input; I only saw its keyword table.
- Browser support references for `String.prototype.normalize` and Unicode property escapes (`\p{ID_Start}`) were not fetched (verified only in Node 24 locally).
- Multi-token keyword phrases containing spaces (for example "vai na frente") were not researched because the brief's keywords are underscore-joined.
- Oxc's regex-scanning function was not located in its lexer sources; only its documentation claim and re-lex functions were read.

## 2. Syntax tree representation: AST versus lossless CST with trivia

### Takeaway
The fastest production JS parsers (oxc, esbuild, acorn, meriyah) use a plain AST with offsets and keep comments and tokens in side channels, while Roslyn, rust-analyzer/rowan, Biome and tree-sitter use lossless trees with trivia because their products are IDE, formatter and refactoring tooling. For a keyword-aliasing transpiler a lossless CST is not required, but the token and trivia layer should be lossless so a CST can be added when a formatter or LSP is built.

### Cited Findings

#### Lossless trees (Roslyn, rowan, Biome, tree-sitter)
- Roslyn syntax trees have three stated attributes: "full fidelity" (every token, white space, comment and preprocessor directive), they "can produce the exact text that they were parsed from", and they are "immutable and thread-safe"; their purposes are tools such as "an IDE, add-ins, code analysis tools, and refactorings" and creating or rearranging code "without having to use direct text edits" — [Roslyn syntax model](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-syntax)
- Roslyn trivia is attached to tokens: "a token owns any trivia after it on the same line up to the next token", later trivia belongs to the following token, the first token gets the initial trivia and the zero-width end-of-file token gets the final trivia; positions are 32-bit zero-based `char` indexes, and each node has `Span` (without trivia) and `FullSpan` (with trivia) — [Roslyn syntax model](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-syntax)
- Roslyn error handling: "a full syntax tree that is round-trippable to the source is exposed" even for syntax errors, using zero-width missing tokens (`IsMissing`) and skipped tokens attached as `SkippedTokensTrivia` — [Roslyn syntax model](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-syntax)
- Red-green trees: the green tree is immutable, persistent, parent-less, built bottom-up, and stores widths not absolute positions; the red tree is an immutable façade built top-down on demand and discarded on every edit, giving parent references and absolute positions; costs are complexity and memory if façades grow large (the page's commentary also mentions many small objects and GC pressure) — [Lippert, Persistence, façades and Roslyn's red-green trees](https://ericlippert.com/2012/06/08/red-green-trees/)
- rust-analyzer's tree is "lossless, or full fidelity", with GreenNodes holding data and red SyntaxNodes plus a typed AST as views; invalid input is wrapped in `ERROR` nodes, missing required nodes are simply absent, parser errors live in a separate sink, and the typed AST layer has all-optional fields to tolerate broken code — [rust-analyzer syntax docs](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/syntax.md)
- rust-analyzer: incremental reparse is a heuristic limited to a single `{}` block and the authors say it matters little for IDE use "since parsing from scratch is fast enough"; green nodes are interned per file — [rust-analyzer syntax docs](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/syntax.md)
- Biome builds on an internal fork of rowan; its CST is "very similar to an AST" but keeps all information "trivia included"; leading trivia runs up to the token including line breaks and trailing trivia runs to the next line break; "bogus" nodes wrap code the parser cannot recover cleanly (`while {}` recovers with a "missing `(`" error, `function}` yields a `JsBogusStatement`) — [Biome architecture](https://biomejs.dev/internals/architecture/)
- tree-sitter's stated goals: general, "fast enough to parse on every keystroke", "robust enough to provide useful results even in the presence of syntax errors", dependency-free; it builds a concrete syntax tree and updates it incrementally, and ships an official JavaScript (Wasm) binding — [Tree-sitter docs](https://tree-sitter.github.io/tree-sitter/)
- matklad (resilient parsing): "For resilient parsing, we want the AST to contain every detail about the source text"; a homogeneous tree "does not enforce any constraints on the shape of the syntax tree at all" so errors can appear anywhere; trivia can be omitted from the parser and attached in a later pass, non-doc comments generally attaching to the following node; his characterization of tree-sitter is that GLR is strong on small valid fragments but weak at assembling "incomplete larger fragments" — [Resilient LL Parsing Tutorial](https://matklad.github.io/2023/05/21/resilient-ll-parsing-tutorial.html)

#### Plain ASTs with side channels (oxc, esbuild, acorn, meriyah, Babel, TypeScript)
- Oxc uses an AST (arena-allocated) rather than a CST; its benchmark authors state "it is not an apple to apple comparison with Biome" because "Biome's parser produces a CST instead of an AST, which requires a lot more work" — [Oxc parser architecture](https://oxc.rs/docs/learn/architecture/parser.html), [Oxc parser benchmark repo](https://github.com/oxc-project/bench-javascript-parser-written-in-rust)
- oxc-parser's JS API returns comments as a separate `comments` array and offers an opt-in `range` option ("`[number, number]` ... start/end offsets of the node in the file contents", default false) and `preserveParens` — [oxc-parser 0.154.0 index.d.ts](https://cdn.jsdelivr.net/npm/oxc-parser@0.154.0/src-js/index.d.ts)
- esbuild stores "a single integer offset per AST node", the start byte of the construct; consequence: "it's not possible to merge ASTs from two separate files and still have source maps work"; symbols live in a flat array and the scope tree "is not attached to the AST" — [esbuild architecture.md](https://raw.githubusercontent.com/evanw/esbuild/main/docs/architecture.md)
- acorn produces an ESTree AST and delivers tokens and comments through `onToken` and `onComment` callbacks with optional `locations`/`ranges` — [acorn README](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/README.md); Meriyah also emits ESTree — [Meriyah README](https://raw.githubusercontent.com/meriyah/meriyah/main/README.md)
- astring (ESTree code generator, works with acorn/meriyah output) generates comments only "provided they are stored on the AST nodes", using Astravel to attach them — [astring README](https://raw.githubusercontent.com/davidbonnet/astring/main/README.md)
- Babel: `attachComment` (default attaches comments to adjacent nodes, `false` skips for speed), `tokens`, `ranges`, `createParenthesizedExpressions` (default marks `extra.parenthesized`); its AST deviates from ESTree (`StringLiteral`, `ClassMethod`, ...) and "The `estree` plugin can revert these deviations" — [Babel parser docs](https://babeljs.io/docs/babel-parser)
- TypeScript's scanner tracks both `getTokenFullStart()` (including leading trivia) and `getTokenStart()`; its parser creates zero-width "missing" nodes for absent tokens — [TypeScript 5.9 scanner.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/scanner.ts), [parser.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/parser.ts)
- [local] TypeScript 5.9.3 on the malformed input `let x = ;\nlet y = 1 +;\nfunction (` returns a tree whose `getFullText()` equals the input exactly (round-trip) and whose absent pieces appear as zero-width identifier nodes — [verify-ts.mjs](file://<scratchpad>/bench-scripts/verify-ts.mjs)
- magic-string exists for "light modifications" of source text with sourcemap generation, as an alternative to AST-based tools such as recast that preserve formatting — [magic-string README](https://raw.githubusercontent.com/Rich-Harris/magic-string/master/README.md)
- Oxc's npm package returns ESM import/export information directly "to avoid walking the AST again" so callers can rewrite imports "with the help of magic-string, without any AST manipulations" — [oxc-parser 0.154.0 README](https://cdn.jsdelivr.net/npm/oxc-parser@0.154.0/README.md)

### Inferences
- Decision rule from the sources: lossless CST earns its cost when the product includes a formatter, an LSP (rename, semantic tokens, code actions) or codemods (Roslyn's and rust-analyzer's stated purposes; Biome's formatter/linter), or when trees of broken code are the primary input. For transpile-only use, the AST-plus-side-channels design of oxc/esbuild/acorn is enough.
- For a mostly 1:1 token-aliasing dialect, the cheapest way to preserve comments and formatting in the output is edit-based codegen: keep the original text and replace token or node ranges (the magic-string pattern, also used by Oxc's own ESM guidance). That needs only `start`/`end` offsets per node and a token list, no comment attachment, and yields exact source maps. Structural sugar that expands to several JS tokens can still be done as range replacements.
- Recommended minimal data model (my synthesis of what acorn, oxc and Babel expose): lossless token array (`kind`, `start`, `end`, `newlineBefore`, `hasEscape`), trivia/comment ranges, and ESTree-shaped AST nodes carrying `start`/`end`. ESTree compatibility keeps `astring`, ESLint-style walkers and the acorn/meriyah/oxc outputs usable as test oracles (differential comparison), which a Babel-shaped AST would complicate.
- Use the Roslyn/Biome convention if trivia is later attached to tokens (trailing trivia to end of line, the rest leading to the next token); it is the only convention stated by two independent lossless implementations.
- Red-green sharing and incremental reparse are not justified at GoiásScript scale: rust-analyzer itself says incremental reparse matters little because full parsing is fast, and playground programs are kilobytes. A simple immutable tree with lazily computed parents is enough if a CST is ever added.

### Gaps
- No like-for-like measurement of lossless CST vs AST cost exists in what I found (Oxc's own benchmark says the Biome comparison is not apples to apples).
- Lippert's page did not discuss trivia or full-width spans; the Roslyn docs page did not discuss performance.
- Biome's page does not explain why a CST was chosen over an AST and marks its formatter and linter sections "work in progress".
- How TypeScript recovers comments (by scanning trivia ranges from `pos`) was not verified; only the scanner's two start positions were.
- No numbers found for rowan-style trees compiled to WASM.

## 3. Hand-written parsing technique for JS-like grammars

### Takeaway
Acorn, meriyah, esbuild, oxc and TypeScript are all hand-written recursive-descent parsers that use a precedence parameter (Pratt/precedence climbing) for expressions, and they resolve the arrow/destructuring ambiguity by one of three techniques: parse as an expression and reinterpret with deferred errors (acorn, esbuild, oxc), speculative lookahead with rollback (TypeScript, oxc for TS), or scan-ahead with lexer-state restore (esbuild). Parse speed will not matter for GoiásScript-sized inputs; the real cost is implementing and maintaining full modern JS grammar plus early errors.

### Cited Findings

#### Technique
- Pratt (1973): the approach is "very simple to understand, trivial to implement, easy to use, extremely efficient in practice if not in theory ... Moreover, it deals nicely with error detection"; Pratt blames "our universal preoccupation with BNF grammars" for it being overlooked — [Pratt, Top Down Operator Precedence](https://tdop.github.io/); Crockford summarizes it as combining "the best properties of Recursive Descent and Floyd's Operator Precedence" — [Crockford, Top Down Operator Precedence](https://crockford.com/javascript/tdop/tdop.html)
- matklad: Pratt parsing "uses both loops and recursion", is "an enhancement of recursive descent", encodes associativity by making left/right binding powers asymmetric, treats prefix, postfix, indexing and ternary as variations of the same loop, and is "one of the most frequently used techniques for hand-written parsing" — [Simple but Powerful Pratt Parsing](https://matklad.github.io/2020/04/13/simple-but-powerful-pratt-parsing.html)
- Expression parsing carries a precedence parameter in the production parsers: TypeScript `parseBinaryExpressionOrHigher(precedence)` / `parseBinaryExpressionRest(precedence, leftOperand, pos)` — [TypeScript 5.9 parser.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/parser.ts); esbuild `parseExprCommon(level, errors *deferredErrors, flags)` and `parseSuffix(left, level, errors, flags)` — [esbuild js_parser.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_parser/js_parser.go); acorn `parseExprOp(left, leftStartPos, leftStartLoc, minPrec, forInit)` — [acorn expression.js](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/src/expression.js)

#### Cover grammars and speculation
- acorn parses an expression while recording would-be pattern errors in a `DestructuringErrors` record (`shorthandAssign`, `doubleProto`, `trailingComma`, `parenthesizedAssign`), converts the expression with `toAssignable` when `=` follows, and otherwise raises the recorded errors via `checkExpressionErrors` — [acorn expression.js](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/src/expression.js)
- esbuild threads a `deferredErrors` argument through expression parsing; `parseParenExpr` "assumes that the open parenthesis has already been parsed by the caller"; `checkForArrowAfterTheCurrentToken` implements "backtracking by restoring the lexer's memory to its original state"; scopes created while the arrow-vs-parenthesized ambiguity is open are discarded or flattened (`popAndDiscardScope`/`popAndFlattenScope`) — [esbuild js_parser.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_parser/js_parser.go), [esbuild architecture.md](https://raw.githubusercontent.com/evanw/esbuild/main/docs/architecture.md)
- Oxc has a `CoverGrammar` trait that converts `Expression` into `AssignmentTarget`, `ArrayExpression` into `ArrayAssignmentTarget`, `ObjectExpression` into `ObjectAssignmentTarget` and so on, and parser `checkpoint`/`rewind`/`lookahead` primitives — [Oxc grammar.rs](https://raw.githubusercontent.com/oxc-project/oxc/main/crates/oxc_parser/src/js/grammar.rs), [Oxc cursor.rs](https://raw.githubusercontent.com/oxc-project/oxc/main/crates/oxc_parser/src/cursor.rs)
- TypeScript's `isParenthesizedArrowFunctionExpression()` returns a three-valued result (True, False, Unknown) and for Unknown does a `lookAhead` that "speculatively look[s] ahead to be sure, and rollback if not"; it also has an "ERROR RECOVERY TWEAK" that parses a standalone `=>` as an arrow function — [TypeScript 5.9 parser.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/parser.ts)

#### Structure, scale and conformance
- esbuild has "only three full-AST passes": (1) lexing, parsing, scope setup, symbol declaration; (2) binding, constant folding, lowering, mangling; (3) printing and source map generation; TypeScript is parsed "by augmenting the existing JavaScript parser" where "most of it just involves skipping over type declarations as if they are whitespace" — [esbuild architecture.md](https://raw.githubusercontent.com/evanw/esbuild/main/docs/architecture.md)
- Oxc: parser is hand-written recursive descent ("Custom implementation for maximum performance") with arena allocation; claimed [vendor] conformance: "100% pass rate" on Test262, 99.62% of Babel parser tests, 99.86% of TypeScript compiler tests (methodology not described); `ParserReturn` guarantees "a structurally valid AST, even if there are syntax errors" but it "may be semantically invalid" — [Oxc parser architecture](https://oxc.rs/docs/learn/architecture/parser.html), [Oxc lib.rs](https://raw.githubusercontent.com/oxc-project/oxc/main/crates/oxc_parser/src/lib.rs)
- Oxc separates syntax errors from early/semantic errors: by default it does not report errors that need scopes, for example `let foo; let foo;`, unless `showSemanticErrors: true`, which "has a small performance cost" — [oxc-parser 0.154.0 README](https://cdn.jsdelivr.net/npm/oxc-parser@0.154.0/README.md)
- Test262 negative tests carry `phase: parse` meaning "the stage ... expected to be produced ... occurs while parsing the source text, or while checking it for early errors" — [Test262 INTERPRETING.md](https://raw.githubusercontent.com/tc39/test262/main/INTERPRETING.md)
- The live ECMAScript spec now includes `using` declarations among the restricted productions, so the grammar target is still moving — [ECMA-262, Lexical Grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html)
- Meriyah describes itself as "100% compliant, self-hosted javascript parser with high focus on both performance and stability" and supports "ESNext Stage 3 features"; its `src/parser.ts` is 304,297 bytes (9,774 lines) and `src/` totals 496,529 bytes in 25 files — [Meriyah README](https://raw.githubusercontent.com/meriyah/meriyah/main/README.md), [Meriyah tree](https://api.github.com/repos/meriyah/meriyah/git/trees/main?recursive=1); its published benchmark page rendered no data when fetched — [Meriyah performance page](https://meriyah.github.io/meriyah/performance)
- Source sizes of reference parsers (GitHub tree API, bytes): acorn `acorn/src` 27 files, 255,063 including generated Unicode tables — [acorn tree](https://api.github.com/repos/acornjs/acorn/git/trees/master?recursive=1); oxc `crates/oxc_parser/src` 45 files, 961,990 — [oxc tree](https://api.github.com/repos/oxc-project/oxc/git/trees/main?recursive=1); esbuild `internal/js_lexer` 3 files, 99,261 and `internal/js_parser` 11 files, 1,661,530 (parser directory also contains lowering and visiting) — [esbuild tree](https://api.github.com/repos/evanw/esbuild/git/trees/main?recursive=1)
- [local] Line counts: TypeScript 5.9 `scanner.ts` 4,101 lines and `parser.ts` 10,819 lines (includes TS syntax); esbuild `js_lexer.go` 2,665 lines and `js_parser.go` 18,846 lines — [scanner.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/scanner.ts), [parser.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/parser.ts), [js_lexer.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_lexer/js_lexer.go), [js_parser.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_parser/js_parser.go)
- TypeScript 7.0 (announced 2026-07-08) is "a native port of TypeScript built in Go" that kept "the structure and logic of the original codebase"; typical full-build speedups 8x to 12x (VS Code: 125.7 s to 10.6 s); "TypeScript 7.0 does not ship with an API", a new API is expected in 7.1, and `@typescript/typescript6` re-exports the 6.0 API — [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/?p=5246)

### Inferences
- Every parser tested parses half a megabyte in roughly 5 to 25 ms and nine megabytes in 0.08 to 1.2 s in Node [local]; GoiásScript programs and playground snippets are kilobytes, so parser throughput should not drive the choice. Bundle size, diagnostics and maintenance dominate.
- How the AST crosses the JS/native boundary dominates for Rust-based parsers: Oxc's native parse of `typescript.js` is about 26 ms [vendor, M3 Max] but 281 ms from Node with JSON transfer on this machine and 76 to 123 ms with raw transfer or lazy access [local] (different CPUs, so this is consistent with, not proof of, boundary cost dominating). A Rust-to-WASM front-end for GoiásScript should therefore return only generated JS, source map and diagnostics, not an AST.
- The dialect is lexically isomorphic to JS, so the parser can be an ordinary JS parser over token kinds: the word operators (`mais`, `menos`, `pelo_menos`, `num_é`, `é_igualim`) become the same token kinds as `+`, `-`, `>=`, `!`, `===` with the same binding powers; only the spelling-to-kind table is the dialect.
- Choose one cover-grammar technique and use it consistently. In TypeScript, acorn-style deferred-error records are the lightest way to handle destructuring assignment targets; speculative lookahead with rollback (TypeScript style) is simpler to reason about for arrow functions but makes error positions depend on the abandoned path.
- Early errors (duplicate lexical declarations, invalid assignment targets, `break` outside loops, strict-mode rules) are a separate layer: Oxc and Test262 both treat them as distinct from grammar. Plan a scope-aware semantic pass rather than folding them into the parser.
- Scale benchmark for "full modern JS": acorn is about 7k lines and Meriyah's `parser.ts` alone about 9.8k lines of TypeScript; the grammar keeps growing (`using`). A solo-maintained hand-written parser is feasible but is a multi-thousand-line commitment that must track the spec; the existing parsers (acorn, meriyah, oxc) plus Test262 are the natural oracle.
- Testing idea (mine, not sourced): because the dialect is a 1:1 spelling map, a reverse mapper (JS to goianês, token-level) can turn JS corpora (Test262, lodash, TypeScript's own sources) into goianês corpora; the compiler must then reproduce the original JS token stream or AST, giving a large differential test with no hand-written expectations.
- Dated practices: parser generators from BNF as the default route (Pratt's 1973 objection still describes the generator ecosystem; every production JS parser above is hand-written); tokenizer-driven regex heuristics (section 1).

### Gaps
- Meriyah's benchmark page showed no data; no published acorn or Babel parse-time numbers were found; the only cross-parser JS numbers are my single-machine local run.
- No published numbers for parse time of oxc/swc/tree-sitter inside a browser (WASM); I did not benchmark the WASM builds.
- Oxc's documentation page does not discuss cover grammar; the `CoverGrammar` trait was read from source. I did not read esbuild's `parseParenExpr` body, so how it converts parenthesized expressions to arrow parameters is not confirmed beyond the signature and architecture notes.
- TypeScript parse-only performance numbers were not found (the 7.0 post gives full-build numbers only).
- swc's parser design was not examined.

## 4. Error recovery and diagnostic quality (including goianês diagnostics)

### Takeaway
Among five JS parsers given the same malformed input, only TypeScript reported several syntax errors in one run (4), while acorn, meriyah, oxc and Babel (even with `errorRecovery: true`) stopped at the first [local]; multiple errors come from a deliberately resilient design (progress-guaranteed loops, recovery sets that include enclosing contexts, missing and error nodes), as in TypeScript, Roslyn and rust-analyzer. For goianês diagnostics the proven shape is a stable code plus whole-sentence message catalog (TypeScript ships a pt-br catalog of about 2,100 entries; rustc moved to Fluent "asymmetric localization") with Elm/rustc-style structure (exact source excerpt, span labels, help vs note).

### Cited Findings

#### Recovery techniques
- Panic mode "best stood the test of time": "As soon as the parser detects an error, it enters panic mode", then synchronizes by discarding tokens to a chosen grammar rule boundary — [Crafting Interpreters, Parsing Expressions](https://craftinginterpreters.com/parsing-expressions.html)
- Resilient LL parsing: the parser should "recognize as much of the syntactic structure as feasible"; "Rather than guessing what the user meant to write, the parser tries to make sense of what is actually written"; every loop either parses an item, skips a token or breaks to the parent, and "The top-most loop must use the 'skip a token' solution"; "item parsing must consume at least one token (if only to report an error)", enforced with a fuel counter refilled to 256 on each advance; FIRST sets stop greedy parsing; recovery sets are not exactly follow sets and "we also want to recursively include ancestor follow sets into the recovery set"; "Academic literature tends to focus on error repair, and mostly ignores pure resilience" — [Resilient LL Parsing Tutorial](https://matklad.github.io/2023/05/21/resilient-ll-parsing-tutorial.html)
- TypeScript: `parseExpected` reports `'{0}' expected.` at the current token and returns false without throwing; `createMissingNode` inserts zero-width placeholder nodes; `abortParsingListOrMoveToNextToken` skips a token unless `isInSomeParsingContext()` (the token starts or terminates "the current list or any enclosing list"), in which case the list is abandoned so a parent recovers; `parseErrorAtPosition` suppresses a second error "at the same position as the last error" — [TypeScript 5.9 parser.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/parser.ts)
- Roslyn recovers with missing tokens and `SkippedTokensTrivia`; rust-analyzer with `ERROR` nodes and absent required nodes; Biome with "bogus" nodes and states recovery "is not a science" — [Roslyn](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-syntax), [rust-analyzer](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/syntax.md), [Biome](https://biomejs.dev/internals/architecture/)
- esbuild aborts on an unexpected token: `Unexpected()` and `ExpectedString()` log an error and `panic(LexerPanic{})`, recovered once in `Parse()` which returns `ok = false`; the same panic/recover is reused for speculative backtracking; non-fatal errors are de-duplicated ("Don't report multiple errors in the same spot"); it has targeted messages with suggestions, e.g. `"await" can only be used inside an "async" function` with a note "Consider adding the "async" keyword here:" and `Suggestion = "async"` — [esbuild js_lexer.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_lexer/js_lexer.go), [js_parser.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_parser/js_parser.go)
- Oxc: `ParserReturn` distinguishes recovered errors (diagnostics non-empty, full AST, `fatal_error` false) from unrecoverable ones (parser "will abort", program empty, `fatal_error` true); `OxcDiagnostic` has `message`, `span`, `severity`, `help`; the docs claim "Continue parsing after errors" — [Oxc lib.rs](https://raw.githubusercontent.com/oxc-project/oxc/main/crates/oxc_parser/src/lib.rs), [Oxc parser architecture](https://oxc.rs/docs/learn/architecture/parser.html)
- Babel: `errorRecovery: true` "will store the parsing error and try to continue parsing", but "even when this option is enabled, `@babel/parser` could throw for unrecoverable errors"; errors carry `code` (e.g. `BABEL_PARSER_SYNTAX_ERROR`) and `reasonCode` (e.g. `MissingSemicolon`) — [Babel parser docs](https://babeljs.io/docs/babel-parser)
- acorn throws a single `SyntaxError` with `pos`, `loc` and `raisedAt`, appending `(line:column)` to the message — [acorn location.js](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/src/location.js)
- [local] Same malformed input (`let x = ;\nlet y = 1 +;\nfunction (`) on five parsers: acorn 8.19.0 one error `Unexpected token (1:8)`; meriyah 6.1.4 one error `[1:8-1:9]: Unexpected token: ';'` with start/end; @babel/parser 7.29.9 one error `UnexpectedToken` (`code` `BABEL_PARSER_SYNTAX_ERROR`) and with `errorRecovery: true` it still threw the same error; oxc-parser 0.154.0 one error `Unexpected token` at offset 8 with no help text; TypeScript 5.9.3 four diagnostics (1109 `Expression expected.` at 8, 1109 at 21, 1003 `Identifier expected.` at 32, 1005 `')' expected.` at 33) — [verify.mjs](file://<scratchpad>/bench-scripts/verify.mjs), [verify-ts.mjs](file://<scratchpad>/bench-scripts/verify-ts.mjs)

#### Diagnostic design and localization
- rustc diagnostics have a level, an optional code (e.g. `E0308`), a message that "should stand on its own", primary and secondary spans with labels, and sub-diagnostics (`note`, `help`); suggestions carry an applicability (`MachineApplicable`, `HasPlaceholders`, `MaybeIncorrect`, `Unspecified`) and the page advises being "conservative when choosing the level" — [rustc dev guide, Diagnostics](https://rustc-dev-guide.rust-lang.org/diagnostics.html)
- rustc style rules: start `Error`/`Warning`/`Note`/`Help` messages lowercase without trailing punctuation, put code in backticks, avoid "illegal", use `help` for what the user can change and `note` for context, avoid phrasing suggestions as questions ("did you mean"); give an error a code only when its long-form explanation (`--explain`) adds information — [rustc dev guide, Diagnostics](https://rustc-dev-guide.rust-lang.org/diagnostics.html)
- rustc uses Fluent for translatable diagnostics, built on "asymmetric localization" to "decouple the expressiveness of translations from the grammar of the source language"; before it, interpolated strings were "hard to translate because writing a natural-sounding translation might require more, less, or just different interpolation than the English string" — [rustc dev guide, Translation](https://rustc-dev-guide.rust-lang.org/diagnostics/translation.html)
- TypeScript diagnostics are templates with placeholders and numeric codes in `diagnosticMessages.json` (`"'{0}' expected."` is code 1005); `--locale` selects the message language, cannot be set from `tsconfig.json`, and "does not affect emit" — [diagnosticMessages.json](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/diagnosticMessages.json), [TypeScript locale doc](https://raw.githubusercontent.com/microsoft/TypeScript-Website/v2/packages/tsconfig-reference/copy/en/options/locale.md)
- [local] The `typescript@5.9.3` npm package ships `lib/pt-br/diagnosticMessages.generated.json` (the locale directory is `pt-br`; the doc table lists Brazilian Portuguese as `pr-BR`, which looks like a typo) with 2,120 lines of entries keyed `<sanitized text>_<code>`, e.g. `"_0_expected_1005": "'{0}' esperado."`, `"Expression_expected_1109": "Expressão esperada."`, `"Identifier_expected_1003": "Identificador esperado."`; other shipped locales: cs, de, es, fr, it, ja, ko, pl, ru, tr, zh-cn, zh-tw — [verify-ts.mjs](file://<scratchpad>/bench-scripts/verify-ts.mjs), [typescript 5.9.3](https://cdn.jsdelivr.net/npm/typescript@5.9.3/lib/pt-br/diagnosticMessages.generated.json)
- Elm 0.15.1 error messages: "you can make a shockingly huge difference just by thinking about the user experience"; "The error shows the code exactly as you wrote it" with the real line numbers; "Every message has a useful hint"; "color is a huge usability improvement" (red draws attention to the problem); the specific type-error messages needed "no significant changes to the type inference algorithm and imposed no noticeable performance cost" — [Elm, Compiler Errors for Humans](https://elm-lang.org/news/compiler-errors-for-humans), [article source](https://raw.githubusercontent.com/elm/elm-lang.org/master/pages/news/compiler-errors-for-humans.elm)
- Delegua's parser directory contains a `tabela-diagnosticos-sintaticos.ts` (a syntactic diagnostics table) next to `erro-avaliador-sintatico.ts` — [Delegua parser directory](https://api.github.com/repos/DesignLiquido/delegua/contents/fontes/avaliador-sintatico)
- The project's own rule is that user-facing messages are in goianês ("Ô rapaz! Deu ruim aqui...", "Eita! Algo não tá certo...", "Ô sô! Tem um problema aí...") with technical internals in English — [project CLAUDE.md](<repo>/CLAUDE.md)

### Inferences
- "Report several errors per run" is not something delegation to acorn, meriyah, oxc or Babel can provide [local]; it must be designed into an own parser (or taken from TypeScript or tree-sitter style tooling). Babel's `reasonCode` is the only machine-readable error identity I saw among the delegation candidates; oxc exposes no documented stable code in the fields I verified.
- Resilience checklist assembled from TypeScript and matklad: the lexer never throws (emits an error token plus a diagnostic); `expect` returns a boolean and a missing node instead of throwing; every loop either consumes a token or exits (progress invariant, optional fuel counter); the recovery set is the union of the first/terminator tokens of all enclosing contexts (TypeScript's `isInSomeParsingContext`, matklad's "ancestor follow sets"); suppress a second error at the same position; keep the tree structurally valid so semantic checks and the LSP still run, but do not emit JS when any error exists (the playground can offer a best-effort preview).
- Message catalog design: stable code per diagnostic, severity, primary span plus secondary labels, positional arguments, optional `help` with an applicability level (enables LSP quick-fixes). Prefer whole-sentence templates per diagnostic, not composed fragments: TypeScript's generic `'{0}' esperado.` hard-codes masculine agreement in Portuguese even when `{0}` is a feminine noun, which is the interpolation problem rustc's Fluent migration describes. Since goianês is a register of Portuguese rather than another language, one catalog (goianês) plus an optional neutral catalog for CI logs is the likely shape; the code makes both testable.
- Tone: keep the goianês voice in a short headline and keep the factual explanation precise and in the same structure rustc and Elm use (exact source excerpt, labelled span, then `help`/`note`); lowercase-no-period rules are rustc-specific, but "say what is wrong, then what to change" carries over. Always name keywords by their goianês spelling in messages, which delegating to a JS parser would break because its messages quote JS token spellings.
- Dialect-aware diagnostics are cheap and high-value for users arriving from JS (idea, not sourced): a plain identifier equal to a JS keyword (`const`, `function`, `console`) can produce "isso é JS; em goiano é `uai`", and pt-BR numeric habits (`1.000,50`) can get a dedicated hint.
- Older practices: fail-on-first-error parsers (esbuild, acorn, meriyah) are acceptable for bundlers but not for an educational language where the first message is the product; textbook panic mode with per-production synchronization tokens is the 'old' form, resilient LL with recovery sets is the one used by current tooling.

### Gaps
- Elm's later error-message writing (0.16 to 0.19) was not fetched; only the 0.15.1 article was read.
- I found no study of localized-diagnostic impact on learners and nothing specific to goianês or other dialect-register languages.
- rustc's documentation shows the Fluent infrastructure, but I did not verify which non-English bundles are actually shipped.
- Oxc's recoverable-versus-fatal boundary is not documented; my single sample produced one error, so which constructs recover is unknown. Babel's list of recoverable errors was not enumerated. Tree-sitter's and Biome's recovery were not tested empirically.
- The runtime cost of resilient parsing (extra recovery paths, error-node allocation) was not quantified.

## 5. Strategy options: own front-end versus delegating to a JS parser versus parser generators

### Takeaway
Only option (a), an own lexer plus own parser, honestly supports the claim "hand-written lexer and parser" and gives full control of goianês diagnostics, at the price of implementing full modern JS grammar and early errors; delegating (b) saves that work but forces the lexer to solve regex/property-name ambiguities without parser feedback, returns JS-worded single-error diagnostics, and makes the parser someone else's; generators (c) cannot make the claim and the JS grammars found are ES5/ES6-era or need hand-written predicates. A hybrid (a) front-end that uses acorn/meriyah/oxc only as test oracles and mature libraries for back-end chores (source maps) is the most defensible reading of the owner's goal.

### Cited Findings

#### (a) Own front-end
- Scale of the work: acorn about 7k lines (255 KB with generated tables), Meriyah 496 KB across 25 files, TypeScript scanner plus parser about 15k lines, esbuild lexer plus parser about 21k lines — see section 3 for sources.
- Conformance harness exists: Test262 with `negative` / `phase: parse` metadata for syntax and early errors — [Test262 INTERPRETING.md](https://raw.githubusercontent.com/tc39/test262/main/INTERPRETING.md)

#### (b) Own lexer, delegate parsing and codegen

- Tools for the remapping step: `@jridgewell/remapping` takes "sequential sourcemaps through transformations" so transformations "only need to generate an output sourcemap"; magic-string generates maps for text edits — [remapping README](https://raw.githubusercontent.com/jridgewell/sourcemaps/main/packages/remapping/README.md), [magic-string README](https://raw.githubusercontent.com/Rich-Harris/magic-string/master/README.md)

### Inferences
Synthesis table (my judgment from the findings; speed is not a differentiator for kilobyte inputs):

| Option | Full modern JS | Browser size | goianês diagnostics | Solo maintenance | Honest "hand-written lexer and parser" |
|---|---|---|---|---|---|
| (a) own lexer + own parser + own emit | Must implement grammar and early errors; acorn/meriyah scale is 7k to 10k lines | Own code; acorn 29 KB and meriyah 35 KB brotli are the reference scale | Full control: codes, resilient recovery, custom messages | Highest up-front work; no upstream coupling; must track the spec (`using`) | Yes |
| (b1) own lexer to JS text, then acorn/meriyah/oxc/Babel, remap positions | Inherited | acorn 29 KB, meriyah 35 KB, Babel 64 KB, oxc wasm 341 KB brotli | Poor: JS-worded messages, one error per run, remapping; only Babel has `reasonCode` | Less code, but the lexer must solve regex vs division and keyword vs property name alone | Lexer only, and the lexer is handicapped |
| (b2) acorn plugin (`Parser.extend`) | Inherited | 29 KB | acorn errors are plain strings, one per parse | Medium; depends on acorn internals with no documented stability | Lexical layer yes, parser no |
| (c1) tree-sitter (fork tree-sitter-javascript, swap keywords) | Via fork | runtime 66 KB wasm + 26 KB js (brotli) + grammar wasm (unmeasured) | Error-tolerant CST; messages must be synthesized from the tree | Medium; C external scanner, grammar toolchain | No (generated parser) |
| (c2) PEG/combinators (Ohm, Peggy, Chevrotain) | Examples stop at ES5/ES6 | Ohm 21 KB brotli | Generic "expected one of" style | Grammar plus hand-coded ASI/regex | No |
| (c3) ANTLR | Grammar exists; needs host predicates per target | runtime unmeasured | Generic | Predicates in each target language | No |

- (b1) is structurally ill-posed: a context-free token mapper cannot know that `obj.trem` or `{ trem: 1 }` must keep `trem` (JS allows reserved words as property names, [local] result in section 1), nor decide regex vs division and template `}` without parser feedback, which is exactly what TypeScript, esbuild and oxc obtain from the parser. Fixing that means embedding a parser in the lexer, at which point the claim and the effort advantage are both gone. The only technically sound delegation is (b2), where the dialect hooks live inside acorn's own tokenizer-parser feedback loop.
- Honest claim by option: (a) yes; (b1) and (b2) can claim "hand-written lexer layer plus acorn/Meriyah/Babel/oxc parser"; (c) can claim "grammar-driven". If the owner's goal is a verifiable "hand-written lexer and parser", only (a) is defensible.
- Practical shape of (a) that limits risk (my synthesis): token-kind-driven Pratt parser; resilient recovery from day one; ESTree-shaped AST with offsets; edit-based codegen with magic-string-style source maps (section 2 and 6); a separate semantic pass for early errors; and acorn, meriyah, oxc and Test262 (through the reverse-mapping idea in section 3) as differential oracles, so the "battle-tested parser" is used for verification rather than as the product.
- Rust-to-WASM alternative: the only full JS/TS parser size datum is oxc at about 341 KB brotli of WASM; a hand-written Rust front-end would have to hand back only strings and diagnostics (section 3) and add a toolchain the TypeScript project does not have; for a solo maintainer in a TypeScript/Node repo, TypeScript is the lower-friction choice unless a measured need appears.
- Delegua demonstrates that a hand-written TypeScript lexer/parser for a Portuguese-keyword language with multiple dialects is maintainable by a small community, and that dialect = keyword table plus lexer subclass; GoiásScript's advantage is that its grammar is JS's, so the parser needs no dialect forks.

- Chevrotain's bundle size was not measured (the URL guessed 404ed); Peggy-generated parser size, ANTLR JS runtime size, the size of a goianês tree-sitter grammar wasm, and `@babel/standalone` were not measured.
- No source confirms that any parser generator covers current ECMAScript (ES2025+); tree-sitter-javascript's and ANTLR's grammar coverage were not verified, and licensing for forking was not checked.

## 6. Source positions and source maps (v3 / ECMA-426)

### Takeaway
Use UTF-16 code-unit offsets internally: that is what JS strings, acorn, TypeScript, Roslyn, LSP's mandatory default and ECMA-426 columns for JavaScript all count, and oxc-parser's JS API also returns UTF-16 offsets (verified for non-BMP and decomposed input). Source maps are version 3 with VLQ segments of 1, 4 or 5 fields; for a dialect whose output is mostly 1:1 token substitution, token-precise maps are cheap to produce from the front-end's own offsets.

### Cited Findings
- ECMA-426 "Source map format specification", 1st edition, December 2024 (drafts at tc39.es/ecma426): "The source map format does not have version numbers anymore, and it is instead hard-coded to always be '3'"; the `version` field "shall always be the number 3 as an integer" — [Ecma International, ECMA-426](https://ecma-international.org/publications-and-standards/standards/ecma-426/), [ECMA-426 draft](https://tc39.es/ecma426/)
- ECMA-426 fields: `file`, `sourceRoot`, `sources` (strings or `null`), `sourcesContent` (optional, "used when the source cannot be hosted"), `names` (optional), `mappings`, `ignoreList` (indices of third-party sources such as "framework code or bundler-generated code"); `mappings` segments "are made up of 1, 4, or 5 variable length fields": one field = generated code with no original source (e.g. "generated by a compiler"), four = mapped without a name, five = mapped with a name — [ECMA-426 draft](https://tc39.es/ecma426/)
- ECMA-426 positions: columns are "computed as UTF-16 code units for JavaScript and CSS source maps" ("A" measures 1 code unit, U+1F525 FIRE measures 2); base64 VLQ values are limited to 32-bit; "Using a data URI along with sourcesContent allows for a completely self-contained source map" — [ECMA-426 draft](https://tc39.es/ecma426/)
- LSP 3.17: positions are zero-based `line` and `character`; the offset unit is negotiated via `PositionEncodingKind` (`utf-8`, `utf-16`, `utf-32`), and UTF-16 "is the default and must always be supported by servers" — [LSP 3.17 specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)
- Roslyn positions are 32-bit zero-based `char` indexes with `Span` and `FullSpan` — [Roslyn syntax model](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/work-with-syntax); TypeScript's scanner keeps `getTokenFullStart()` and `getTokenStart()` — [TypeScript 5.9 scanner.ts](https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/compiler/scanner.ts)
- esbuild stores one start offset per node, computes error ranges by re-scanning (`RangeOfIdentifier(source, loc)`), and notes that merging ASTs from different files breaks source maps; its printer emits "a VLQ-encoded sequence of source map offsets" per file that is later rebased — [esbuild architecture.md](https://raw.githubusercontent.com/evanw/esbuild/main/docs/architecture.md), [esbuild js_lexer.go](https://raw.githubusercontent.com/evanw/esbuild/main/internal/js_lexer/js_lexer.go)
- Oxc is natively UTF-8 and merged "feat(ast): implement utf8 to utf16 span converter" on 2025-01-24 — [oxc PR #8687](https://github.com/oxc-project/oxc/pull/8687); [local] oxc-parser 0.154.0 returned UTF-16 offsets in both default and `experimentalRawTransfer` modes for a source starting with a string holding U+1F525 and `é` followed by `const a = 1;` (UTF-16 index 7, UTF-8 offset 10, oxc `start` 7) and for an NFD identifier source (index 12, UTF-8 offset 13, oxc `start` 12), identical to acorn — [verify.mjs](file://<scratchpad>/bench-scripts/verify.mjs), [oxc-parser 0.154.0](https://cdn.jsdelivr.net/npm/oxc-parser@0.154.0/src-js/index.d.ts)
- Source-map tooling: magic-string "manipulating strings and generating sourcemaps"; `@jridgewell/remapping` composes sequential maps; astring accepts a `sourceMap` generator (from the `source-map` module) — [magic-string](https://raw.githubusercontent.com/Rich-Harris/magic-string/master/README.md), [remapping](https://raw.githubusercontent.com/jridgewell/sourcemaps/main/packages/remapping/README.md), [astring](https://raw.githubusercontent.com/davidbonnet/astring/main/README.md)
- Oxc exposes a `range` option producing `[start, end]` node offsets (default false) — [oxc-parser 0.154.0 index.d.ts](https://cdn.jsdelivr.net/npm/oxc-parser@0.154.0/src-js/index.d.ts); Babel offers `ranges` — [Babel parser docs](https://babeljs.io/docs/babel-parser); acorn offers `locations`/`ranges` — [acorn README](https://raw.githubusercontent.com/acornjs/acorn/master/acorn/README.md)

### Inferences
- Position model: store UTF-16 offsets (`start`, `end`) in tokens and nodes, keep a line-start table, and compute line and column lazily; convert to UTF-8 only at a Rust/WASM boundary or when an LSP client negotiates `utf-8`. Because NFC normalization is applied to token text only (section 1), spans stay in original coordinates and a decomposed `é` correctly counts as 2 UTF-16 units in both diagnostics and source maps.
- Nodes may carry only `start` (esbuild's choice) if `end` is recomputed for diagnostics, but a goianês compiler that wants underline spans and edit-based codegen should store `end` too; memory is irrelevant at this scale.
- Own codegen through range edits yields token-precise mappings directly (generated column from the edit, original position from the token), so no map composition is needed; remapping libraries matter only if a second transformation stage (minifier, bundler) or a delegated parser is added. If a JS parser is delegated (option b), diagnostics need a per-token interval table from the lexer's rewrite to map JS-text offsets back to goianês offsets.
- For the playground: embed `sourcesContent` and use a data-URI map so DevTools shows `.gs` source; use `ignoreList` for any injected runtime shim (for example the `prosa` helper) so stepping skips it.
- A one-field segment is the right encoding for compiler-generated code with no goianês origin (shims, wrappers).

- Sizes of source-map libraries (magic-string, `@jridgewell/gen-mapping`, `source-map`) were not measured.
- astring's need for node `loc` to build mappings was not verified; only the README's statement that it supports a source map generator.
- ECMA-426 drafts may add features after the 1st edition (the text I read had no debug-ID or scopes fields; I did not look for later proposals), and browser DevTools support for `ignoreList` and `names` was not verified.
- Display-column handling (tabs, East Asian width, combining marks) in diagnostic renderers was not researched.
- oxc's UTF-16 conversion was verified on two small inputs only; the PR title alone does not establish that every JS API path converts.
